# LightPrism 序列规范 v0.1

> 本文是 `<D:…>` / `<CODE>` / `<V:…>` **语法与校验规则的唯一事实源**。
> 代码实现：[`src/lightprism/sequence.py`](../src/lightprism/sequence.py)、
> [`src/lightprism/tokens.py`](../src/lightprism/tokens.py)。规范与实现不一致时以本文为准，
> 并由 `tests/test_sequence.py` 兜住回归。

## 一、四类片段

| 片段 | 语法 | 可携带内容 |
|---|---|---|
| 任务 | `<TASK>自由文本</TASK>` | 中文自然语言（中文 BPE 侧） |
| 决策 | `<D:POINT=OPTION>` | `POINT` 为 `[A-Z_]+`，`OPTION` 为 `[A-Z0-9_]+` |
| 代码 | `<CODE>\n光明代码\n</CODE>` | 光明源码（代码 token 侧） |
| 验证 | `<V:CODE>` | `CODE` 为 `PASS` / `WARN=…` / `ERR=…` |

**白空间规则**：控制 token 之间只允许空白。任何裸露文本（既不在 `<TASK>` 里、
也不在 `<CODE>` 里）都是解析错误 —— 不允许「猜这段文本属于谁」。

## 二、决策点清单（v0.1 首批 7 个）

| 决策点 | 选项 | 含义 |
|---|---|---|
| `EDIT` | `FR` / `RW` / `PATCH` | find-replace / 整文件重写 / 补丁式修改 |
| `SAFE` | `L0` / `L1` / `L2` | 安全等级：L0/L1 自动执行，L2 人工确认 |
| `RETRY` | `YES` / `NO` | 验证失败后是否重试 |
| `FIX` | `ADD_TYPE` / `RENAME` / `REFACTOR` | 按错误类型选修复方向 |
| `NEXT` | `TEST` / `EDIT` / `ASK` | 继续测试 / 继续编辑 / 请求人工 |
| `CTX` | `KEEP` / `DROP` / `FETCH` | 记忆门控 |
| `PLAN` | `DECOMPOSE` / `DIRECT` | 是否拆分子任务 |

规则：

1. **选项顺序即优先级**（探针 argmax 取第一个命中项），改动顺序等于改动模型语义，
   必须同步升 `TokenSpace.schema_version`。
2. 选项集合**封闭**：未登记的选项解析即报错，绝不静默兜底。
3. 单点选项数控制在 2—8 个。

### 已知缺口：`<D:EDIT=NEW_FILE>`

原始方案 §2.1 的示例使用了 `NEW_FILE`，但 §4.2 首批表里没有它。本仓库的处置是
**解析即报错**（`ParseError`），把缺口暴露在测试里，而不是悄悄接受一个词表外的 token。
补法：新增 `EDIT` 选项 `NEW_FILE` 并在预算表 `decision` 槽位内重新核算，同步升 schema 版本。

## 三、验证码清单（v0.1，8 个）

| 验证 token | 触发条件 |
|---|---|
| `<V:PASS>` | 无 error 级诊断、无 warning |
| `<V:WARN=NON_CANONICAL>` | 只有 warning（L1005/L1007/L3002/L3003/L3004/L5002/L5003） |
| `<V:ERR=MISSING_TYPE>` | L2002（布尔/空值写法） |
| `<V:ERR=TYPE_MISMATCH>` | L2001 / L2003 |
| `<V:ERR=UNDEFINED_VAR>` | L3001 / L4001 |
| `<V:ERR=IMPORT_FAIL>` | L4002 |
| `<V:ERR=SYNTAX>` | L1001 / L1002 / L1003 / L1004 / L1006 |
| `<V:ERR=CHECKER_FAIL>` | L0000、L5001，以及**任何未登记的新诊断码** |

映射函数：`map_diagnostics()`。规则是确定性的 —— 取**第一个 error 级诊断**的码去查表，
查不到就落 `ERR=CHECKER_FAIL` 并在 `detail` 里写明未登记的码。这样新错误码会被暴露，
而不是被静默归并成某个「最像」的类别。

> **口径说明**：原始方案 §5 的映射表用的是语义名（`MISSING_TYPE` 等），而 `light ai check`
> 的真实输出是 `Lxxxx` 诊断码（见 `light/src/diagnostics/registry.py`，19 条规则）。
> 本项目保留语义名作为 token，但映射源必须是真实诊断码 —— 否则「与真实返回一一对应」就是空话。

## 四、结构校验规则

`ParsedSequence.validate()` 返回**问题列表**（空 = 合法），一次报全不短路。

| # | 规则 | 默认 | 说明 |
|---|---|---|---|
| 1 | 必须有 `<TASK>` 段 | 开 | `require_task=False` 可关（用于续写片段） |
| 2 | 决策 token 必须在词表内 | 开 | 点与选项都要登记过 |
| 3 | 每个 `<V:…>` 前面必须是 `<CODE>` 段 | 开 | 验证只能针对代码，不能凭空出现 |
| 4 | 连续两个决策 token 之间必须有代码 | **关** | 见下 |

规则 4 为什么默认关：原始方案 §2.1 的示例本身就写了 `<D:PLAN=DECOMPOSE>` 紧跟
`<D:EDIT=FR>` —— 「先规划、再定编辑策略」是合法的复合决策。这条只在阶段三做 RL 惩罚
「为了决策而决策」时按需打开：`validate(forbid_consecutive_decisions=True)`。

## 五、决策密度

`decision_density(items)` = 决策 token 数 / 序列项数，上限 `CONTROL_TOKEN_MAX_RATIO = 0.02`
（与原始方案 §8 第 5 条一致）。

注意这是**按段计数**的粗粒度指标。训练侧的细粒度密度按子词 token 统计，两者数值不可直接
比较；探针实验报告里必须写明用的是哪一种（见[探针实验设计](探针实验设计.md) §4）。

## 六、版本与兼容

- `TokenSpace.schema_version` 当前 `0.1`。
- 以下任一变更都必须升版本，并在 CHANGELOG 里写明：
  新增/删除/重排决策点或选项、新增/删除验证码、改变 `<V:…>` 的映射源。
- 只增不改是目标：新增决策点走「保留区」额度，不改动既有 token 的文本形态。
