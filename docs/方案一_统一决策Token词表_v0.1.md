# 方案一：统一决策 Token 词表（Light-Decision-Token）技术方案

**版本**：v0.1  
**日期**：2026-11-11  
**定位**：在 Light 光明语言 64K 词表约束下，把“决策”编码为词表中的特殊 token，与光明代码 token、验证反馈 token 共享同一个自回归序列和同一套下一 token 预测损失，实现决策与生成在**序列层面**的协同，而不是外挂两个模型互相调用。

---

## 一、为什么方案一在 Light 上成立的概率较高

Chameleon 已经证明：把图像离散成 8192 个码本 token，与文本 BPE token 放进同一个约 40K 的词表，用单一 Transformer 做自回归“下一 token 预测”，可以让“看”和“写”共享同一个序列建模过程。Emu3 进一步表明，统一的自回归架构在异构任务上不会必然导致性能崩塌，前提是词表设计和训练目标足够精细。

Light 的条件比 Chameleon 更有利：

1. **词表完全可控**。Light 的 L0 核心字只有 30 个，L1/L2 语法层级是人为设计的，高频语法组合可以从真实项目语料中统计，而不是靠通用 BPE 去猜。
2. **决策空间天然离散且封闭**。光明编程中的“编辑策略选择”“安全等级判断”“是否重试”都是从有限选项中选一个，天然适合编码为特殊 token。
3. **验证信号是确定性的**。`light ai check` 的错误类型有限且稳定，可以映射为验证反馈 token，模型可以直接在序列中消费，而不是读一段自然语言再“理解”。
4. **64K 是一个足够紧的预算**。词表越紧凑，决策 token、代码 token、验证 token 在同一个嵌入空间里的距离越近，模型越不需要在几种分布之间“跳远”。

**核心判断**：方案一不是“把三个模型合并成一个参数集”，而是**把三类信息统一成同一种序列语言**。决策不再是外挂分类器，而是自回归过程中的一个“词汇选择”；验证不再是后置脚本，而是序列中可被模型消费的反馈 token。

## 二、总体设计

### 2.1 序列形态

模型看到的训练序列和推理序列遵循同一种交错结构：

```text
<TASK>实现一个按文件大小排序并输出前10名的CLI工具</TASK>
<D:PLAN=DECOMPOSE>
<D:EDIT=NEW_FILE>
<CODE>
设 文件列表 为 列目录(".")
...
</CODE>
<V:PASS>
<D:NEXT=TEST>
<CODE>
...
</CODE>
<V:ERR=MISSING_TYPE line=7 expected="int">
<D:FIX=ADD_TYPE>
<CODE>
...
</CODE>
<V:PASS>
```

关键点：

- `<D:...>` 是**决策 token**，表示在当前位置做出的封闭选择。
- `<CODE>...</CODE>` 是光明代码 token 序列。
- `<V:...>` 是**验证反馈 token**，由 `light ai check` 的结果确定性映射而来。
- 三者共享同一个词表和同一个下一 token 预测目标。模型在生成 `<D:EDIT=FR>` 之后，后续代码 token 的分布应当与“find-replace”策略一致；生成代码后，必须跟随一个 `<V:...>` token，且该 token 与真实验证结果对齐。

### 2.2 与 lightharness 的关系

方案一不替代 lightharness。lightharness 继续负责：

- 项目级上下文外置与检索；
- 工具调用（文件读写、命令执行、`light ai check` 调用）；
- 多轮任务循环与人工确认节点。

方案一改变的是**模型内部**：决策不再通过“调用另一个决策模型”完成，而是在生成序列中直接输出决策 token。lightharness 只需要把模型输出中的 `<D:...>` 解析为结构化动作，把 `<V:...>` 作为下一轮输入的一部分。

| 通用代码 token 余量 | 8K—12K | 数字、运算符、标点、常见标识符片段 |
| **决策 token** | **128—512** | 每个封闭选择点一组互斥 token，见第四节 |
| **验证反馈 token** | **64—256** | `light ai check` 错误类型与通过状态的确定性映射，见第五节 |
| 保留/扩展 | 1K—2K | 后续新增决策点、实验性 token、特殊控制符 |

**硬约束**：

- L0 核心字必须保证“一字一 token”。任何 L0 字被拆成两个 token，都会破坏 Light 最底层的稳定性假设。
- 决策 token 的命名空间要与代码 token 明确隔离，避免模型把 `<D:...>` 当成普通标识符生成。

## 四、决策 Token 规范

### 4.1 设计原则

1. **封闭性**：每个决策点对应的 token 集合必须覆盖所有合法选项，不能出现“没有 token 可选”的情况。
2. **互斥性**：同一决策点内的 token 互斥，模型一次只能选一个。
3. **可解析性**：lightharness 能无歧义地把 `<D:...>` 解析为结构化动作。
4. **可扩展性**：保留命名空间前缀，后续新增决策点不破坏已有 token。

### 4.2 首批决策点建议

从子程序地图中优先选择 5—8 个高频、封闭、可验证的决策点：

| 决策点 | Token 示例 | 选项来源 |
|---|---|---|
| 编辑策略 | `<D:EDIT=FR>` / `<D:EDIT=RW>` / `<D:EDIT=PATCH>` | find-replace / 整文件重写 / 补丁式修改 |
| 安全等级 | `<D:SAFE=L0>` / `<D:SAFE=L1>` / `<D:SAFE=L2>` | L0/L1 自动执行，L2 以上人工确认 |
| 是否重试 | `<D:RETRY=YES>` / `<D:RETRY=NO>` | 验证失败后的下一步 |
| 修复方向 | `<D:FIX=ADD_TYPE>` / `<D:FIX=RENAME>` / `<D:FIX=REFACTOR>` | 根据验证错误类型选择 |
| 下一步动作 | `<D:NEXT=TEST>` / `<D:NEXT=EDIT>` / `<D:NEXT=ASK>` | 继续测试 / 继续编辑 / 请求人工 |
| 上下文检索 | `<D:CTX=KEEP>` / `<D:CTX=DROP>` / `<D:CTX=FETCH>` | 记忆门控 |
| 任务分解 | `<D:PLAN=DECOMPOSE>` / `<D:PLAN=DIRECT>` | 是否拆分子任务 |

每个决策点的 token 数量建议控制在 2—8 个，首批总决策 token 数在 128—512 之间。

### 4.3 决策 Token 的监督信号来源

不需要人工逐条标注。决策 token 的监督信号可以从以下历史记录中**自动导出**：

- `light ai check` 的验证日志：在什么代码状态下，验证通过/失败，失败类型是什么；
- lightharness 的工具调用记录：模型或人类在某个状态下调用了哪个工具、传了什么参数；
- 人类在 Light 项目中的实际编辑序列：修改了哪个文件、用了 find-replace 还是整文件重写、修改后是否通过验证；
- 任务分解树：树形任务流中每个节点的完成状态与结果。

导出规则示例：

- 如果一次编辑是通过 find-replace 完成的，且随后 `light ai check` 通过，则该位置标注 `<D:EDIT=FR>` + `<V:PASS>`；
- 如果验证返回 `MISSING_TYPE`，且下一次编辑增加了类型标注并通过，则标注 `<V:ERR=MISSING_TYPE>` + `<D:FIX=ADD_TYPE>` + `<V:PASS>`；
- 如果某次命令执行被人工确认拦截，则标注 `<D:SAFE=L2>`。

## 五、验证反馈 Token 规范

`light ai check` 的输出需要被**确定性映射**为验证 token，而不是自然语言。建议映射表：

| `light ai check` 结果 | 验证 token |
|---|---|
| 通过 | `<V:PASS>` |
| 缺少类型标注 | `<V:ERR=MISSING_TYPE>` |
| 未定义变量 | `<V:ERR=UNDEFINED_VAR>` |
| 类型不匹配 | `<V:ERR=TYPE_MISMATCH>` |
| 模块导入失败 | `<V:ERR=IMPORT_FAIL>` |
| 语法错误 | `<V:ERR=SYNTAX>` |
| 规范非强制警告 | `<V:WARN=NON_CANONICAL>` |
| 验证器自身超时/异常 | `<V:ERR=CHECKER_FAIL>` |

**关键要求**：验证 token 必须与 `light ai check` 的真实返回**一一对应**，不能由模型“自己判断”验证结果。训练时，序列中的 `<V:...>` 由真实验证器生成，而不是模型生成；推理时，模型生成 `<V:...>` 后，lightharness 仍需实际调用 `light ai check` 做最终确认。模型学会的是“预测验证结果并据此调整后续生成”，而不是“替代验证器”。

## 六、训练课程

方案一最大的风险不是“学不会”，而是 1B 模型在同时学习两种异质任务时出现训练塌缩或决策校准丧失。训练必须分阶段。

### 阶段一：词表共存（约 20% 训练量）

**目标**：让决策 token、代码 token、验证 token 在嵌入空间中进入同一个“语义场”，消除分布错配。

**数据形态**：序列中随机交错三类 token，但**不要求**模型在决策 token 之后必须生成对应代码，也**不要求**验证 token 与代码严格因果对齐。损失函数为标准的下一 token 预测，不做特殊加权。

**检查点**：阶段一结束后，用余弦相似度分布检查决策 token 的嵌入向量是否与代码 token 落入同一个可分子空间；同时跑第七节的探针实验。

### 阶段二：序列内协同（约 50% 训练量）

**目标**：让决策真正为后续代码生成设定“策略上下文”。

**数据形态**：序列严格遵循“决策 → 代码 → 验证”的交错模式。模型在生成 `<D:EDIT=FR>` 之后，后续代码 token 分布应与 find-replace 策略一致；生成代码后必须跟随 `<V:...>` token，且该 token 与真实 `light ai check` 结果对齐。

**关键**：这一步是方案一“协同”发生的地方。决策不再是外挂分类器，而是自回归过程中为后续生成设定条件的 token。

### 阶段三：RLVR 微调（约 30% 训练量）

**目标**：让决策 token 的校准性对齐到最终结果，而不是停留在“看起来合理”。

**奖励设计**：

- 如果模型在决策 token 后生成的代码通过 `light ai check`，给予正向奖励；
- 如果验证失败并返回 `<V:ERR=...>`，模型在后续序列中生成修复决策和修复代码并通过验证，给予修复奖励；
- 如果模型选择 `<D:SAFE=L2>` 但实际动作被人工拦截，给予负向奖励；如果选择 `<D:SAFE=L0>` 且动作安全执行，给予正向奖励；
- 对决策 token 的过度使用（例如在不需要决策的地方频繁输出 `<D:...>`）给予轻量惩罚，防止模型“为了决策而决策”。

**训练环境一致性**：RLVR 的奖励信号必须与 lightharness 部署时看到的工具反馈一致。训练中模型看到的 `<V:...>`，就是部署时 `light ai check` 返回的映射结果。

## 七、最小验证实验：20% 训练成本回答“通不通”

不需要等完整训练跑完。阶段一结束后，做一个判别性实验。

### 7.1 实验设置

- **底座**：Qwen2.5-Coder-1.5B 或选定的 1B 级底座；
- **词表扩展**：按第三节预算加入决策 token、验证 token、Light 高频语法组合；
- **训练**：只完成阶段一“词表共存”训练；
- **探针**：冻结生成头，只训练一个线性分类器（参数量在 1M 以下），从模型对决策 token 的隐藏状态中预测“下一步应该选哪个编辑策略/安全等级/是否重试”。

### 7.2 三组对照

| 组别 | 配置 |
|---|---|
| **A 组（外挂）** | 独立轻量决策模型（如 LightDec / GLiNER2.5-Decide）+ 原生成模型，通过 lightharness 编排 |
| **B 组（纯生成）** | 不加入决策 token，纯生成模型 + 后置 `light ai check` |
| **C 组（方案一探针）** | 完成阶段一词表共存训练，用线性探针从决策 token 隐藏状态读决策 |

### 7.3 通过标准

C 组需同时满足：

1. **决策准确率**：探针读出的策略选择准确率 **不低于 A 组独立决策模型**；
2. **生成质量**：生成代码的一次通过率 **不低于 B 组**；
3. **格式合法率**：模型输出中 `<D:...>` / `<CODE>` / `<V:...>` 的序列格式合法率 **≥ 95%**；
4. **无退化信号**：决策 token 密度不超过总 token 的 2%，且生成速度下降不超过 15%。

如果四条同时满足，说明决策 token 已经在共享表征中获得有意义的编码，“共存”前提成立，可以推进阶段二。如果不满足，优先调整：

- 词表预算分配（决策 token 是否过多/过少）；
- 阶段一训练数据中决策 token 与代码 token 的共现比例；
- 决策 token 的嵌入初始化方式；
- 探针的训练数据是否与决策点分布匹配。

**警惕信号**：如果探针准确率很高，但生成代码通过率显著下降，说明决策 token 正在挤占生成能力。需要降低决策 token 密度、减少决策 token 数量，或检查阶段一数据中是否“决策样本”占比过高。

## 八、稳定性保障

Chameleon 的经验表明，多模态 token 早期融合时，如果没有 QK-Norm 和 LayerNorm 顺序调整，训练会在约 20% 进度处发散。方案一的异质性低于图像+文本，但 1B 模型容量更紧，以下措施不是“调优技巧”，而是**必要条件**：

1. **QK-Norm**：在注意力点积之前对 query 和 key 投影施加 LayerNorm，从第一个 token 开始启用。
2. **LayerNorm 顺序调整**：采用预归一化结构，并确保决策 token 与代码 token 共享同一归一化路径。
3. **决策 token 早期融合**：决策 token 从训练第一步参与嵌入学习，不后期注入。
4. **学习率分层**：决策 token 和验证 token 的嵌入学习率可以略高于代码 token，但不超过 2 倍；训练中期逐步衰减到同一水平。
5. **决策 token 密度上限**：训练数据中决策 token 占总 token 比例控制在 1%—2%，避免模型过度关注“做选择”。
6. **梯度裁剪**：按 token 类型分别监控梯度范数，如果决策 token 梯度持续显著高于代码 token，说明损失权重失衡，需要调整数据配比。

## 九、评估体系

### 9.1 任务集

- **Light 编程窄任务**：20—30 个典型任务，覆盖单函数、小模块、CLI 工具、文件处理脚本；
- **系统维护工具调用**：10—15 个任务，覆盖磁盘查询、进程诊断、服务状态检查、临时文件清理；
- **跨模块重构/调试小项目**：2—3 个 Light 小型项目，每个 5—15 个文件。

### 9.2 指标

| 指标 | 含义 | 目标 |
|---|---|---|
| 决策 token 校准误差（ECE） | 决策置信度与实际正确率之差 | 越低越好，阶段三后应低于独立决策模型 |
| 探针准确率 | 从隐藏状态读决策的准确率 | 不低于 A 组 |
| 一次通过率 | 单次生成通过 `light ai check` 的比例 | 不低于 B 组，阶段三后显著高于 B 组 |
| 闭环可用率 | 验证反馈 + 1—2 次重试后人工判定可用的比例 | 作为最终用户体验指标 |
| 序列格式合法率 | `<D>`/`<CODE>`/`<V>` 结构合法比例 | ≥ 95% |
| 决策 token 密度 | 决策 token 占总 token 比例 | ≤ 2% |
| 端到端延迟 | 含验证器的完整闭环耗时 | 相对 A 组不上升 |
| 峰值显存/内存 | 推理时资源占用 | 8GB 显存或纯 CPU 可运行 |

## 十、风险与边界

1. **决策 token 挤占生成能力**：1B 容量有限，决策 token 过多或训练数据中决策密度过高，会导致代码生成质量下降。缓解：决策 token 预算不超过 1%—2%，阶段一探针实验提前发现退化。
2. **决策校准丧失**：如果验证 token 由模型“自判”而非真实验证器生成，校准会迅速失真。缓解：训练和推理中 `<V:...>` 始终以真实 `light ai check` 结果为准。
3. **词表碎片化**：L0 核心字被拆碎、高频语法组合未合并，会破坏 Light 的底层稳定性。缓解：L0 一字一 token 硬约束，L1/L2 组合从真实语料统计后合并。
4. **数据偏差**：训练数据中某些决策点样本过少，模型会偏向高频选项。缓解：按决策点分层采样，保证每个选项都有足够正负样本。
5. **1B 容量上限**：方案一在 1B 上成立，不代表能覆盖所有复杂任务。边界仍然是“窄任务、强验证、可复现”，跨模块重构和复杂调试需要 lightharness 的子程序编排配合。
6. **不替代 lightharness**：方案一是模型内部的序列协同，不是替代项目级上下文管理、工具调用和人工确认。lightharness 仍然是编排层。

- 从 Light 真实项目、`light ai check` 日志、lightharness 工具调用记录中导出决策 token 监督信号，形成第一版训练数据 schema；
- 实现 `light ai check` 结果到 `<V:...>` token 的确定性映射表；
- 选定 1B 底座，完成词表扩展和嵌入初始化。

### 第 1 个月

- 完成阶段一“词表共存”训练（约 20% 训练量）；
- 跑第七节探针实验，产出 C 组 vs A/B 组的对照报告；
- 如果通过标准满足，进入阶段二；如果不满足，调整词表预算和数据配比后重跑阶段一。

### 第 2 个月

- 完成阶段二“序列内协同”训练（约 50% 训练量）；
- 在 Light 窄任务集上评估一次通过率、序列格式合法率、决策 token 密度；
- 迭代 lightharness 对 `<D:...>` / `<V:...>` 的解析与执行逻辑。

### 第 3 个月

- 完成阶段三 RLVR 微调（约 30% 训练量）；
- 跑 2—3 个 Light 小型项目的端到端闭环，记录失败模式；
- 产出方案一技术报告：词表设计、训练课程、探针实验、端到端指标、与 A/B 组对照；
- 根据结果决定是否将方案一模型作为 light.quye.com 的“统一决策-生成”推荐模型发布，并在 jikuai 文档中提供可选接入示例。

---

## 十二、一句话总结

方案一不是“把三个模型合并成一个参数集”，而是**把决策、代码、验证统一成同一种序列语言**：64K 词表里，L0 核心字保证 Light 的底层稳定，高频语法组合压缩代码长度，决策 token 让“选择”成为自回归过程中的一个词汇，验证 token 让 `light ai check` 的确定性信号直接进入模型上下文。20% 训练量的探针实验先用最低成本回答“通不通”，通过后再用“共存 → 协同 → RLVR”三阶段课程把方案一推到可交付状态。
