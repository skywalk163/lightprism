# 样本导出

> 把 light 与 lightharness 的**真实日志**转成 LightPrism 训练样本。
> 代码：`src/lightprism/exporters/`。方案依据：`docs/方案一_统一决策Token词表_v0.1.md` §4.3。

## 一、总原则（三条，每个导出器都要遵守）

1. **跳过必须计数**，不允许静默丢弃。`ExportStats` 的每项跳过都有对应字段，且
   `coverage` 是唯一诚实的覆盖率指标。
2. **不编造**：日志里没有的字段不许猜。任务意图、通过结论、修复方向，能推的推、
   推不了的留空并在 `problems` 里说明。
3. **数据源格式必须写明出处**：源码路径 + 行号，或真实样例。不许「大概是这个形状」。

## 二、已实现：`light ai check` 报错归档

### 2.1 数据源的真实形状

核对自 `light/cli/light.py` 与 `light/tools/ai_copilot/error_corpus.py`（2026-11-11）：

| 项 | 事实 |
|---|---|
| 落盘位置 | `$LIGHT_ERROR_CORPUS_DIR` 或 `~/.light/error_corpus/<YYYY-MM>.jsonl` |
| 字段 | `ts` / `last_seen` / `code` / `message` / `hint` / `fixes` / `source_snippet` / `source_hash` / `lang_level` / `backend` / `light_version` / `hits` |
| 归档范围 | **只归档 error 级诊断**（`_ai_archive_diagnostics` 里 `severity == 'error'`），PASS 与 warning 不入档 |
| 去重 | 同一 `(code, source_hash)` 只落一行；命中时只更新 `index.json` 的 `hits`/`last_seen` |
| 片段长度 | `SNIPPET_RADIUS = 2`（±2 行），`MAX_SNIPPET_CHARS = 2000` |
| hash 算法 | 换行归一化后 `sha256(...)[:16]` |

### 2.2 结构性限制：**导不出修复样本**（这是结论，不是欠账）

`source_hash` 是对**出错那一刻**的源码算的。两条路都走不通：

- 代码没改 → hash 能匹配 → 但现跑必然仍失败；
- 代码改好了 → 现跑会通过 → 但 hash 变了，永远匹配不上那条记录。

实测确认：把 `/tmp/lp_src/snippet.light` 从 `打印(甲[9])` 改成 `打印(甲[0])` 后，
hash 从 `3f8e1a3acc644768` 变成 `1284d1e5c731b464`，该记录直接落到 `skipped_no_source`。

**所以本导出器只产出失败样本**，并显式声明 `produces_repair_samples: false`。

能导出的两种：

| 情形 | 产物 | 标记 |
|---|---|---|
| hash 匹配 + 现跑仍失败 | `EDIT=FR` + `<CODE>` + `V:ERR=<码>` | `meta.live_check="still_failing"` |
| hash 匹配 + 现跑通过了 | 同上（**仍不造 PASS 步骤**） | `meta.stale=true`、`live_check="pass_now"` |

第二种在实践中几乎不可达（hash 相同却结果不同，只可能是检查器行为变了），
但它必须被正确标记 —— 现跑通过**不等于**模型学会了修复。

### 2.3 用法

```bash
# 只导失败样本（快，不跑代码）
PYTHONPATH=src python -m lightprism export \
    --source-root /home/skywalk/dswork/light/stdlib \
    --out data/exported.jsonl

# 附带现跑复核（慢：每条都要真跑 light ai check --run）
PYTHONPATH=src python -m lightprism export \
    --source-root /path/to/sources \
    --light-root /home/skywalk/dswork/light \
    --min-hits 2 --limit 500 \
    --out data/exported.jsonl
```

### 2.4 为什么必须带 `--run`

`light ai check` 不带 `--run` 时**只做语法检查**，运行时类错误（L3001 索引越界、
L5001 后端不支持）一律返回 `ok: true`。实测：

```
不带 --run：{"ok": true,  "diagnostics": []}                     ← 越界代码被判通过
带   --run：{"ok": false, "diagnostics": [{"code": "L3001"}]}    ← 正确
```

导出器若默认不跑，会把「根本没修」的样本标成「已通过」。所以 `LightChecker`
默认 `run=True`，这不是性能取舍。

## 三、本轮修掉的两个映射错误

导出真实 corpus 时发现的，属 v0.1 建表时的语义失误：

| 诊断码 | 原映射 | 改为 | 理由 |
|---|---|---|---|
| `L3001` 列表索引越界 | `ERR=UNDEFINED_VAR` | `ERR=RUNTIME` | 越界不是「变量不存在」 |
| `L5001` 后端不支持 | `ERR=CHECKER_FAIL` | `ERR=RUNTIME` | 那是编译期能力边界，不是验证器故障 |

验证码因此从 8 个增至 9 个（新增 `ERR=RUNTIME`）。这两个错误会让模型学到错误的因果关联：
「越界 → 去找未定义变量」，方向完全反了。

## 四、下一个来源：lightharness 编辑日志（未实现）

修复样本只能从**记录了「编辑前后」的日志**里来：

| 需要的字段 | 为什么 |
|---|---|
| 文件路径 | 才能把「改之前」与「改之后」关联起来 |
| 编辑方式（FR / RW / PATCH） | 直接给出 `EDIT` 决策，不用推断 |
| 编辑前后的 check 结果 | 给出 `V:ERR=…` → `V:PASS` 的配对 |
| 时间戳与任务 id | 用于把多步归到同一个任务 |

**现状**：`lightharness` 目前没有这种日志格式（2026-11-11 核对：`logs/` 下只有
`T4_watch.jsonl` 这类进程监控，`data/finetune/*.jsonl` 是代码语料不是调用序列）。
要落这个来源，得先在 lightharness 侧定义并写入该格式，再回来写解析器。

在拿到那个格式之前，写一个「猜格式」的解析器没有意义 —— 会产出一批看起来像样本、
实际字段全错的数据。

## 五、导出样本长什么样

```json
{
  "task": "修复光明代码中的错误（L3001）：索引错误 列表索引越界（rt:2）",
  "source": "light_ai_check",
  "steps": [{
    "decisions": {"EDIT": "FR"},
    "code": "设 甲 为 [1, 2]\n打印(甲[9])\n",
    "validation": "ERR=RUNTIME",
    "validation_detail": "索引错误 列表索引越界（rt:2）"
  }],
  "meta": {
    "corpus_code": "L3001",
    "source_hash": "3f8e1a3acc644768",
    "hits": 2,
    "stale": false,
    "live_check": "still_failing",
    "fix_derived": "REFACTOR"
  }
}
```

`task` 字段是**模板化的**，不是真实意图：归档里只有错误码和消息，没有「用户当时想做什么」。
把它写成「修复 XX 错误」是诚实的最小值；硬编一个具体任务描述就是编造。

## 六、已知限制

- 覆盖率天然偏低：要求记录能匹配到当前源文件，且源文件在 `--source-root` 范围内。
  实测本机 corpus 3 条记录 → 2 条是 L0000 用法错误、1 条源文件不在扫描目录，导出 0 条。
- `hits` 依赖 `index.json`；索引被清过则退回到 JSONL 里的值（恒为 1）。
- 多文件内容完全相同时取路径最短的那份，可能不是报错发生时的那份（内容一致，影响有限）。
- 不解析 `source_snippet` 作为代码体 —— ±2 行不构成可编译样本，宁可跳过。
