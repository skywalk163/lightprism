# LightPrism 设计方案

> 版本 v0.1 · 2026-11-11 · 本文是[方案一_统一决策Token词表_v0.1.md](方案一_统一决策Token词表_v0.1.md)
> 的工程化整理，不含原始方案里未定论的探索段落。编号引用（§三、§七…）均指原始方案文档。

## 一、一句话

不是「把三个模型合并成一个参数集」，而是**把决策、代码、验证统一成同一种序列语言**：
64K 词表里，L0 核心字保证 Light 的底层稳定，高频语法组合压缩代码长度，决策 token 让「选择」
成为自回归过程中的一个词汇，验证 token 让 `light ai check` 的确定性信号直接进入模型上下文。

## 二、为什么在 Light 上成立的概率较高

Chameleon 已证明把图像离散成码本 token 与文本 BPE 放进同一词表、用单一 Transformer 做
下一 token 预测是可行的。Light 的条件更有利：

1. **词表完全可控**。L0 只有 44 个单字（冻结表），L1/L2 语法是人为设计的，
   高频语法组合可以从真实项目语料统计，而不是靠通用 BPE 去猜。
2. **决策空间天然离散且封闭**。编辑策略、安全等级、是否重试都是从有限选项里选一个。
3. **验证信号是确定性的**。`light ai check` 的错误类型有限且稳定（19 条诊断规则），
   可映射为验证 token，模型直接在序列中消费，而不是读一段自然语言再「理解」。
4. **64K 是一个足够紧的预算**。词表越紧凑，三类 token 在同一个嵌入空间里的距离越近，
   模型不需要在几种分布之间「跳远」。

## 三、序列形态

```text
<TASK>实现一个按文件大小排序并输出前10名的CLI工具</TASK>
<D:PLAN=DECOMPOSE>
<D:EDIT=FR>
<CODE>
设 文件列表 为 列目录(".")。
...
</CODE>
<V:PASS>
<D:NEXT=TEST>
<CODE>
...
</CODE>
<V:ERR=MISSING_TYPE line=7 expected="int">
<D:FIX=ADD_TYPE>
<CODE>
...
</CODE>
<V:PASS>
```

语法细节（含 `line=` / `expected=` 这类携带信息的位置）见[序列规范](序列规范.md)。
**v0.1 骨架只实现到「不携带附加字段」的形态**：`<V:ERR=SYNTAX>`，不带 `line=…`。
原因是附加字段的解析与词表覆盖需要单独一轮设计（见序列规范「已知缺口」），
先保证主干的封闭性与可解析性，再扩展。

## 四、与 lightharness 的分工

LightPrism 不替代 lightharness。lightharness 继续负责项目级上下文外置与检索、工具调用、
多轮任务循环与人工确认节点；LightPrism 改变的是**模型内部**：决策不再通过「调用另一个
决策模型」完成，而是在生成序列中直接输出决策 token。

lightharness 的适配面只有两处：

- 把模型输出里的 `<D:…>` 解析成结构化动作（`TokenSpace.parse_decision`）；
- 把 `<V:…>` 作为下一轮输入的一部分，并在推理后仍然真实调用 `light ai check`。

## 五、三阶段训练课程

| 阶段 | 训练量 | 数据形态 | 目标 |
|---|---:|---|---|
| 一 · 词表共存 | 20% | 三类 token 随机交错，不要求因果对齐 | 三类 token 进入同一「语义场」，消除分布错配 |
| 二 · 序列内协同 | 50% | 严格「决策 → 代码 → 验证」交错 | 决策为后续生成设定策略上下文 |
| 三 · RLVR 微调 | 30% | 同上 + 奖励信号 | 决策校准对齐到最终验证结果 |

阶段一结束后必须跑[探针实验](探针实验设计.md)，用 20% 成本回答「通不通」，不通过不进入阶段二。

**阶段一的判定标准**（四条同时满足）：

1. 探针读出的策略选择准确率 ≥ A 组独立决策模型；
2. 生成代码一次通过率 ≥ B 组纯生成模型；
3. `<D>`/`<CODE>`/`<V>` 结构合法率 ≥ 95%；
4. 决策 token 密度 ≤ 2%，生成速度下降 ≤ 15%。

## 六、稳定性保障（必要条件，非调优技巧）

1. **QK-Norm**：注意力点积前对 Q/K 投影施加 LayerNorm，从第一个 token 起启用。
2. **预归一化**：决策 token 与代码 token 共享同一归一化路径。
3. **早期融合**：决策/验证 token 从训练第一步参与嵌入学习，不后期注入。
4. **学习率分层**：决策/验证 token 嵌入学习率可略高于代码 token，但不超过 2 倍，中期衰减到同一水平。
5. **密度上限**：训练数据中决策 token 占比 1%—2%。
6. **梯度监控**：按 token 类型分别看梯度范数；决策 token 梯度持续显著偏高即为配比失衡。

## 七、评估体系

| 指标 | 含义 | 目标 |
|---|---|---|
| 决策校准误差 ECE | 决策置信度与实际正确率之差 | 阶段三后应低于独立决策模型 |
| 探针准确率 | 从隐藏状态读决策的准确率 | 不低于 A 组 |
| 一次通过率 | 单次生成通过 `light ai check` 的比例 | 不低于 B 组，阶段三后显著高于 B 组 |
| 闭环可用率 | 验证 + 1—2 次重试后人工判定可用 | 最终用户体验指标 |
| 序列格式合法率 | `<D>`/`<CODE>`/`<V>` 结构合法比例 | ≥ 95% |
| 决策 token 密度 | 决策 token 占总 token 比例 | ≤ 2% |
| 端到端延迟 | 含验证器的完整闭环耗时 | 相对 A 组不上升 |
| 峰值显存/内存 | 推理资源占用 | 8GB 显存或纯 CPU 可运行 |

前两项与后两项的**离线段**已在本仓库可算：`lightprism parse` 输出结构合法率与决策密度。

## 八、风险与边界

1. **决策 token 挤占生成能力**：1B 容量有限。缓解：预算 ≤ 2%、阶段一探针提前发现退化。
2. **决策校准丧失**：验证 token 若由模型自判会迅速失真。缓解：训练与推理中 `<V:…>` 一律以真实
   `light ai check` 结果为准；`map_diagnostics()` 只做确定性映射，不含模型判断。
3. **词表碎片化**：L0 字被拆碎会破坏底层稳定性。缓解：`check_l0_atomicity()` 做硬检查。
4. **数据偏差**：某些决策点样本过少会让模型偏向高频选项。缓解：按决策点分层采样。
5. **1B 容量上限**：本方案成立不等于覆盖所有复杂任务。边界仍是「窄任务、强验证、可复现」。
6. **不替代 lightharness**：编排层仍是 lightharness。
