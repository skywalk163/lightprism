# LightPrism 词表预算 v0.1

> 唯一事实源是代码：`src/lightprism/vocab.py` 的 `DEFAULT_BUDGET`。
> 本文是它的推导说明；两者不一致时以代码为准，并由 `tests/test_sequence.py::test_default_budget_sums_to_64k` 兜住。

## 一、预算表

| 槽位 | 建议值 | 区间 | 精确 | 说明 |
|---|---:|---|---|---|
| `l0_core` | 44 | 44 | ✅ | L0 核心字，一字一 token |
| `l1_l2_syntax` | 8192 | 4096—8192 | | L1/L2 高频语法组合 |
| `stdlib_names` | 10240 | 6144—10240 | | 标准库模块/函数/类型名 |
| `chinese_bpe` | 34804 | 30720—36864 | | 中文自然语言 BPE |
| `code_reserve` | 10240 | 8192—12288 | | 数字/运算符/标点/标识符片段 |
| `decision` | 320 | 128—512 | | 决策 token |
| `validation` | 160 | 64—256 | | 验证反馈 token |
| `reserved` | 1536 | 1024—2048 | | 后续决策点/实验 token/控制符 |
| **合计** | **65536** | | | 必须精确等于 64K |

## 二、为什么这样分

1. **L0 冻结区放最前面、精确 44**。方案文档 §3 要求 L0「一字一 token 硬编码，放词表最前面，
   永久冻结，不允许被 BPE 拆分」。数量从方案里的 30 改成 44，依据是
   `light/docs/language/l0-core.md` 的 44 字权威表 —— `light/src/keywords.py` 文件头
   专门写了一段说明为什么旧的「30 字」是错数字。
2. **中文 BPE 吃掉取整余量**。其余七个槽位取整后是 30732，剩余 34804 全部落给中文 BPE。
   把余量放在最大的、弹性最强的槽位，而不是硬凑某个整数。
3. **决策 token 320 而首批只用了 19 个**。首批 7 个决策点共 19 个 token（3+3+2+3+3+3+2），远低于 128 下限。
   这不是浪费：320 是**预留额度**，方案文档要求给「子程序地图里长出来的决策点」留空间，
   同时硬约束是占比 ≤ 2%（320/65536 = 0.49%，还有余量）。
4. **验证 token 160 而首批只用了 8 个**。同上，`light ai check` 的 19 条诊断码只会增加不会减少，
   预留覆盖新码段。
5. **保留区 1536**。方案文档 §3 写「1K—2K，用于后续新增决策点、实验性 token、特殊控制符」。

## 三、核算口径

```bash
PYTHONPATH=src python -m lightprism budget            # 人读表
PYTHONPATH=src python -m lightprism budget --json     # 机器可读
PYTHONPATH=src python -m lightprism budget --set decision 400 --json
```

`VocabBudget.problems()` 检查三件事，任一不通过即返回非空列表：

1. 每个槽位落在区间内（`exact` 槽位必须精确相等）；
2. **合计恰好等于 65536** —— 少分出来的额度必须显式进 `reserved`，不允许「悄悄空着」；
3. 已定义的决策/验证 token 数不超过对应槽位额度，且决策 token 占全词表比例 ≤ 2%。

第 3 条同时依赖 `TokenSpace`：只要新增决策点没同步调预算，测试就会红。

## 四、L0 原子性检查

```bash
PYTHONPATH=src python -m lightprism l0 tokens.json          # {"tokens": ["设","为","若果",...]}
PYTHONPATH=src python -m lightprism l0 tokens.json --light-root /home/skywalk/dswork/light
```

`check_l0_atomicity()` 的判据：任何 L0 字出现在**长度 > 1 的 token** 内部，即认为被拆碎或粘连。
`--light-root` 会尝试 import light 仓的 `src.keywords` 做交叉校验，并把**字表来源**写进输出 ——
因为「用的是哪份表」是口径问题，不能让人以为两种情况下拿到的是同一份权威数据。

## 五、待定项（v0.2 必须回答）

1. `l1_l2_syntax` 与 `stdlib_names` 的区间跨度较大（4096—8192 / 6144—10240），
   真实语料统计后应收到 ±10% 以内，而不是继续用区间中点。
2. 数字 token 的切分粒度（一位一 token vs. 常见整数整体）会显著影响代码 token 密度，
   需要在 `code_reserve` 内部再分一次，当前还没做。
3. 决策 token 的嵌入初始化方式（随机 vs. 由选项名文本的 BPE 向量均值初始化）
   未定，方案文档 §7.3 把它列为探针不达标时的调整项之一。
