**id 布局**：五文本槽（`[0,63520)`）→ reserved 自有段（`[63520,65050)`，段标记在 `64000/64001`）→
decision 预留 301 → validation 预留 151 → 4 结构（`[65502,65506)`）→ 19 已定义决策 →
9 已定义验证 → `<UNK>`(65534) → `<PAD>`(65535)。
控制块落在 `[65502, 65534)`，与 `TokenSpace` 完全对齐；`ControlTokenLayout.finalize()`
要求「ids 恰好是 start..end−1」，这里 32 个 id 连续无空洞。

> 为什么段标记在 64000 而不是 63520：`reserved` 槽在预算表里从 `slot_offsets()["reserved"]=64000`
> 起，但本表为保住控制块末尾连续，把 reserved 自有段排在 decision/validation 预留之前，
> 自有段物理起点是 63520。段标记按唯一事实源落在 64000/64001（自有段内偏移 480），
> 详见 §十一。

**生成质量属于另一张卡**（卡面也写了「demo 验收后另开卡」）。

### 冒烟的诚实边界

- `src/lightprism/demo/train_demo.py` 目前**硬绑** `data/unified/vocab_4096.json`（`resolve_vocab_path()`），
  并且在 `DemoTrainer.__init__` 里用 `vocab.vocab_size` **覆盖** config 的 `vocab_size`。
  该文件不在 T-0373 的 `paths` 内，按契约**未修改**。
  因此 `train_demo --config configs/demo-3m-64k.json --steps 20` 实际仍会用 4096 词表——
  **不要拿它当 64K 证据**。本报告的 64K 证据来自 `--train-smoke` 的进程内注入
  （`monkeypatch` 掉 `load_demo_vocab`，并在启动前对账「config 的 V 与词表 embedding 尺寸一致」，不一致直接报错）。
- 建议后续卡给 `train_demo` 加 `--vocab` 参数并去掉「用词表尺寸覆盖 config」的行为。
- `configs/demo-3m.json` 保持 V=4096 未动，`configs/demo-3m-64k.json` 是新增文件（V=65536、d=192、L=6、H=6）。

2. **`stdlib_names` 池不足**：L0-free 真实名合计 8694 < 10240，缺口 1546 由仓库内其它库模块的
   真实标识符补（`stdlib_repo_identifiers`）。不伪造占位符；预算若要收紧，建议收到 8192 上下并重分配。
3. **`code_reserve` 数字档偏重**：十进制整数 5919 条（占槽 57.8%），是对 `docs/词表预算.md` §五.2
   「数字 token 切分粒度」的显式回答；若后续更偏代码，应压到 1000—2000 并把额度给标点二连/标识符，需重测密度。
4. **中文 n-gram 尾部有 2255 条 f1**：高频池（16916 + 12260）用完后仍有空洞，尾部用 freq=1 的
   纯汉字 5—8 字组合兜底；若要「零 f1」，需扩语料或把槽位降 2.2K。
5. **`train_demo` 加 `--vocab`**（另开卡）：否则 64K 只能靠注入验证。

## 十一、T-0375：64K 表补 `<PY>` / `<LIGHT>` 并重建

### 做了什么

1. `vocab_build.py::build_vocab_64k`：`reserved_own_quota = 1536 − 段标记 2 − 结构标记 4 −
   `<UNK>`/`<PAD>` 2 = **1528**`；段标记按 `vocab.slot_offsets()["reserved"]` 落位，
   与 `SEGMENT_TOKEN_IDS` 同源，装配后再断言一次「`tokens[want] == token`」，错位直接构建失败。
2. 重建 `data/vocab_64k.json` + `data/vocab_64k.manifest.json`：`tokens[64000]='<PY>'`、
   `tokens[64001]='<LIGHT>'`；manifest 新增 `segment_markers` 段，`reserved.charged` 改为
   `{segment_markers:2, own_placeholders_and_specials:1528, structure_markers:4, unk_pad:2}`。
3. `--check-64k` 从 10 项扩到 12 项，新增「段标记 id = SEGMENT_TOKEN_IDS」与
   「reserved 头部 = 段标记」两条硬判据。
4. `tests/test_demo_vocab.py`：新增段标记落位 / 预算 `segment_id_range()` / `DemoVocab`
   编码不产生 UNK 三条用例，并同步 `reserved.charged` 的合计断言。

### 关键口径：段标记为什么是 64000 而不是 63520

`reserved` 槽的两套坐标必须分清：

- **预算坐标**：`vocab.slot_offsets()["reserved"] = 64000`（`DEFAULT_BUDGET` 顺序是
  `… code_reserve → decision → validation → reserved`），`SEGMENT_TOKEN_IDS` 就由它推导；
- **物理坐标**：本表为满足 `ControlTokenLayout.finalize()` 的「已定义控制块必须落在末尾连续
  区间」，装配顺序是 `… code_reserve → reserved 自有段 → decision 预留 → validation 预留 →
   控制块 → UNK/PAD`，自有段物理起点是 **63520**。

两者差 480。把 reserved 物理起点挪到 64000 是**不可行**的：decision 320 + validation 160
恰好等于 480，要占满 `[63520,64000)` 就得把 decision/validation 的已定义 token（19+9）
也搬进这段，而它们必须与 4 个结构标记保持末尾连续——两个约束不可兼得。
因此按唯一事实源把段标记落在 64000/64001，即自有段内偏移 `64000 − 63520 = 480` 处；
`reserved` 槽继续按多段 range 登记（`[[63520,65050], [65502,65506], [65534,65536]]`），
不假装连续。

### 与 T-0373 的差异（同语料、同 light_root 重建）

- `l0_core` / `l1_l2_syntax` / `stdlib_names` / `chinese_bpe` / `code_reserve` / `decision` /
  `validation` 七个槽 token 逐条相同，槽 sha256 与 T-0373 一致；
- 只有 `reserved` 槽变化：`<PY>`/`<LIGHT>` 占住 64000/64001，其后 `<RSV:…>` 顺移，
  末尾去掉 `<RSV:1521>`/`<RSV:1522>`，槽内 1050 个 id 变化；槽 sha256
  `49f913578079 → 11a1ed61b865`。
- 全表 token sha256 `24a51b8a1b70… → 05cd9af7136b…`。

### 未做 / 风险

1. **未改 `vocab.py`**（不在本卡 `paths`）：`SEGMENT_TOKEN_IDS` / `segment_token_ids()`
   仍是唯一事实源，本卡只保证 64K 产物与之对齐；如果预算表顺序将来调整，
   `--build-64k` 会因落点断言直接失败，不会静默错位。
2. **未把 `reserved` 物理起点迁到 64000**：需要重排控制块（会破坏 `ControlTokenLayout`
   的末尾连续性，牵动 `DemoVocab` 与控制区测试），超出本卡「只补两个 token」的范围；
   当前做法在语义上完全等价（encode `<PY>` → 64000，不再落 UNK）。
