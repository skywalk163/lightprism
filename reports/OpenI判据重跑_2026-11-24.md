## 0. 结论先行

1. **③ 的 0.9091 是解码预算问题，不是模型问题，而且加预算已经到头了。** A 组（512）截断只剩 3 条，非截断裸合法率 96.2% 已过 95%；但本卡新增的离线长度核算表明：**55 条 test 目标序列最长只有 434 token**，512 预算对任何样本都不短。也就是说这 3 条截断全部是「模型没在该收尾处吐出 `<V:…>`」，先查停止判据，再谈加预算到 640。
2. **② 两轮不动不是因为「样本数还没加上」，而是 B 这个变量在本数据上恒等于 A。** `subset = splits["test"][:args.eval_gen_samples]`，test 只有 55 行，`--eval-gen-samples 140` 被截成 55。跑 B 只会得到和 A 一样的 47 条 JSON 代理、一样的 2 条差距。
3. **① 已经有坏数字**：A 组 C 探针 0.6667 vs 外挂分类器 0.8889（多数类 0.2222、随机 0.3333）。门禁未过只能记 `unknown`，但数值是实测的——门禁一放开，① 直接判 fail。
4. **④ 取方案乙（不改判据代码）**：判据原文就是「≤2%」只卡上限，密度 0.19% 低于方案 1–2% 区间属**机制覆盖不足**，今后不得再用 ④ pass 充当「机制已验证」。

## 2. 脚本加固（`scripts/openi_run.sh`）

**CUDA 预检（`require_cuda`）**：`run` / `bg` 启动前先判断 `torch.cuda.is_available()`，不可用直接 `exit 3` 并打印三条排查（torch 是否 CPU 版 / 是否分到 CPU 或 NPU 集群 / 镜像是否带 CUDA 运行时），不再像旧版那样静默回落到 `--device cpu`（上一次「显存 0、进度不动」就是这么误判的）。确实要纯 CPU 跑必须显式 `LP_ALLOW_CPU=1`。

**`status` 子命令**：一条命令给全四件事——`pgrep -af train_openi.py`（无 `pgrep` 时退回 `ps -ef | grep`）、`nvidia-smi` 的显存/利用率（并提示「显存 0 且进程在跑 = CPU 在啃」）、最新 `run_*.log` 的头 3 行与末 5 行、`metrics.json` 与 `checkpoints/` 是否落盘。

**`sum` 增补**：除 verdict/evidence_level/每条判据外，直接打印 C、B 两组的 `n_all / n_counted / n_truncated / structure_rate_all / structure_rate(非截断) / JSON exact / 决策密度`，以及 `gate_blockers` 与 `speed_drop_vs_B`——看 0.8x/0.9x 这个小数之前先看截断分母。

## 3. 判据 ③：截断归因（分母口径不动）

| 项 | 首跑（`--max-new-tokens 384`） | A 组（512） |
|---|---|---|
| `n_all` | 52 | 55 |
| `n_truncated` | 6 | 3 |
| `n_counted` | 46 | 52 |
| `structure_rate_all`（计入截断，判据口径） | **0.8077**（42/52） | **0.9091**（50/55） |
| 非截断裸合法率（诊断量，不参与判据） | 42/46 = 91.3% | 50/52 = **96.2%** |
| 距 95% 还差 | 7 条 | 3 条（95% 在 55 条上意味着至少 53 条通过） |

**离线核算（纯标准库，不依赖 GPU）**：按 `build_ids` 复现 55 条 test 的目标序列长度（prompt `[<TASK>]+task+[</TASK>]` 之后的部分）：

| 类别 | 条数 | 目标 token 最大 | 最小 |
|---|---|---|---|
| code | 8 | **434** | 43 |
| task_decomposition | 7 | 184 | 102 |
| file_list | 8 | 151 | 18 |
| config | 10 | 64 | 30 |
| validation | 8 | 48 | 38 |
| diagnostic | 5 | 41 | 37 |
| decision | 9 | 38 | 33 |

- 全部 55 条目标合计 4,546 token，均值 82.7，**最长 434**（`写一个光明程序：第 2 课：做一台计算器——算术运算`，code 类）；每条目标恰好含 1 个 `<V:…>` 验证 token（不存在「数据没给停止位」）。
- 384 预算下**必然截断**的只有 1 条（434 > 384），首跑却截断 6 条 → 另外 5 条是早收尾失败。
- 512 预算下**没有任何样本目标超预算**，A 组仍截断 3 条 → 这 3 条 100% 是「该吐 `<V:…>` 时没吐」的解码控制问题。

**因此**：③ 剩余 3 条不再靠「继续加预算」解决——512 → 640 只能验证「是不是真的就差这百来步」，但根因指向停止判据（`expect_validation=True` 时只认 `<V:…>` 停止）与约束解码路径是否一致。分母 `n_all` 一个字没改，`counted_toward_structure_rate` 口径未动。

## 4. 判据 ②：判别力核算（B 变量无效 + 样本量算术）

**代码事实**（`train_openi.py` 的 `eval_generation`）：`subset = splits["test"][:args.eval_gen_samples]`。test 只有 **55** 行（JSON 47 / code 8），`--eval-gen-samples 140` 被 `[:140]` 截成 55 —— B 与 A 的评估集合完全相同，训练配置相同，**B ≡ A**。所以「差 2 条」不会因为跑 B 而变化。

| 项 | 首跑（`n_all=52`，JSON 44） | A 组（`n_all=55`，JSON 47） |
|---|---|---|
| JSON 代理 n | 44 | **47** |
| C 精确匹配 | **9/44 = 0.204** | **10/47 = 0.213** |
| B 精确匹配 | **7/44 = 0.159** | **8/47 = 0.170** |
| 差距 | 2 条 | **2 条 = 4.3 个百分点** |
| 判据阈值 | `MIN_DECISIVE_GAP = 3` 条 → 47 条上是 **6.4 个百分点** | 同 |

**统计噪声**：47 条、比例约 0.19 时，两组比例差的标准误 `√(2·0.19·0.81/47) ≈ 8.1pp`，95% 半宽约 16pp。也就是说 47 条**只能分辨 16pp 以上的差距**，4.3pp 完全埋在噪声里——这不是「再跑一次运气好就过」，是样本量物理上不够。要以 80% power 检出 4.3pp，需要 **每臂约 1300 条 JSON 代理样本**。

**可执行结论**：
1. 跑 B（哪怕在 V100 上跑一百次）都不会让 ② 变 decisive，别再把「加评估样本数」当待验证变量；
2. ② 只有两条出路：把内嵌 test 的 JSON 代理扩到千条级（新卡 + `embed_payload` 重建，属数据工程，不在本卡 paths），或者明确承认 ② 在本规模只能记 `unknown`、只报「点估计 + 差距条数」；
3. 本轮取后者（不改判据代码），并在报告里写清「2 条 / 4.3pp < 6.4pp 阈值，统计上无判别力」。

## 5. 判据 ①：数值已观测，判据记 unknown

| 项 | 首跑 | A 组（512） |
|---|---|---|
| C 探针宏平均（`EDIT` 点，pos-1 特征） | 与多数类基线持平（等价恒预测多数类） | **0.6667** |
| A 组外挂分类器宏平均 | — | **0.8889** |
| 多数类基线 / 随机基线 | — | 0.2222 / 0.3333 |
| 探针 test 行数 | 9 | 9 |
| 判据结果 | `unknown` | `unknown`（门禁未过） |

unknown 的原因必须写清：**门禁未过（决策点只覆盖 1/7、探针 test 只有 9 行 < 30、train/test 模板簇重合 27），不是没数**。数值本身已经观测：C 0.6667 < A 0.8889 —— 一旦按现状放开判据，① 就是 **fail**，结论是「1 个决策点 + 36 训练/9 测试条支撑不了『统一序列可替代外挂分类器』」。补样本（T-0370）时应按模板簇分组切分，让 A 组也面对跨模板泛化，否则一条「27 簇重合」就把结论否掉。

## 8. 归因表：截断 vs 真非法

| 类别 | A 组（512） | 判据 | 依据 |
|---|---|---|---|
| 截断样本 | 3 条 | 计入全分母，按失败算 | 离线长度核算：52 条目标 ≤434 token，全部 ≤512；故 3 条均为「未按时吐 `<V:…>`」 |
| 真非法（非截断但不合法） | 2 条 | 计入全分母，按失败算 | 50 条非截断里 2 条缺段（缺 `<CODE>` 闭合或缺 `<V:…>`），A 组 jsonl 未回传，缺段类型待复现 |
| 首跑对照 | 截断 6 / 真非法 4 | 同上 | 384 预算下 1 条必然截断（434>384），其余 5 条早停失败 |

**已知的环境缺口**：卡面要求「A 组 3 条截断逐条任务名 + 断到第几个 token、2 条真非法逐条缺哪个段」，这需要 A 组 `lightprism_out/generated_samples.jsonl` 原件；该文件没有随两轮实测回传到本机（`G:\dswork` 与两台内网机都搜过，无 `generated_samples.jsonl`/`metrics.json`）。本卡能做的是：把**可解析字段补齐**（见下）+ 给出结构性归因与复现命令，逐条归因留给下次跑完自动产出。

**字段补齐（`train_openi.py`）**：`generated_samples.jsonl` 原来每条只写 `free_structure_ok` / `free_problems`，**没有 truncated 也没有 token 数**，事后根本分不开「截断」与「真非法」。现新增 `free_truncated`、`free_n_tokens`、`free_n_decision`、`free_tokens_per_s`、`constrained_problems`、`constrained_truncated`，下次任何一轮（含 V100）跑完即可直接统计。

## 10. 遗留风险与下一步

- **③ 的 3 条截断**：先查停止判据与约束解码一致性，再考虑 640；不要用「改分母」的方式美化。
- **④ 口径**：方案乙已落地（只卡上限），但 0.19% 低于 1–2% 目标区间，机制覆盖不足的结论要跟着 ① 一起修。
- **门禁原样**（两轮一致，未动）：
