# LightPrism 探针实验 v2（OpenI/V100）深度评审

> 评审对象：`python lightprism/train_openi.py`（v2，commit `f99f209`）在 OpenI Tesla V100S-PCIE-32GB 上的首轮完整输出。
> 评审日期：2026-11-12。评审口径：`docs/探针实验设计.md` §4/§5/§6/§8、`docs/方案一_统一决策Token词表_v0.1.md` §7/§8。
> 本机复核：`python train_openi.py --self-check` 通过；切分/标签覆盖/密度/任务模板重合均在本机重算过（无 GPU，纯标准库路径可复现）。

---

## 0. 一句话结论

**这轮 `verdict=fail` 是「测量无效」，不是「方案不通」。** v2 修掉的泄漏是真的（v1 的 1.000 确属抄答案），
但当前实验仍然**无法对四条判据中的任何一条做出可信判定**：探针只覆盖 1/7 个决策点、
评估样本只有 7 条且与训练集 100% 模板重合、判据 ③ 的分母有幸存者偏差、
判据 ② 的「通过」只差 1 条样本。按 `next_step` 里写的「§6 固定顺序调参后重跑」是**错的方向**——
这是数据/口径问题，调超参救不回来。**先补数据与口径，再谈调参。**

同时也别把 v2 误读成「方案被证伪」：目前所有数字既不支持 pass，也不支持 fail。

## 1. 先复现判定，确认输出与脚本一致

把 OpenI 输出里的数字回填进 `judge()`，本机复算得到同样的结果：

```
VERDICT: fail   evidence: partial_coverage
  fail  ① 探针准确率 ≥ A 组     | C=0.714 vs A=1.000；随机基线 0.333
  pass  ② 一次通过率 ≥ B 组     | C=0.191 vs B=0.167
  fail  ③ 无约束结构合法率 ≥ 95% | 0.875（仅统计未截断生成）
  pass  ④ 决策密度 ≤ 2% 且速度下降 ≤ 15% | 密度=0.0020，速度下降=0.010
```

脚本本身没跑错，`evidence_level=partial_coverage`、`leakage_suspected=false`、
`shuffle_probe_macro_accuracy=0.5714` 都和它自己的口径自洽。**问题出在口径本身。**

## 2. v2 修对了什么（先记功）

| 修复 | 证据 |
|---|---|
| 探针特征改取 `pos-1`，不再取决策 token 自身位置 | `self_position_control.macro_accuracy=1.0` 而主探针 `0.7143`，两者之差成立，泄漏已消除 |
| V100 强制 fp16 + GradScaler | 日志首行 `SM7.0 native_bf16_tensorcore=False → torch.float16`，没被 `torch.is_bf16_supported()=True` 骗到 |
| UNK 率改按传入序列统计 | `unk_tokens=48`（本机 `--self-check` 同为 48），不再随构建次数翻倍 |
| 判据 ②③ 加 ≥30 样本门槛、日志用 `loss.detach()` | 输出里体现 |

反向哨兵这轮也**正确放行**了：打乱组 0.5714 < `leak_threshold=0.70`。但要提醒一句，
C=0.7143 与打乱组=0.5714 在 n=7、随机基线 0.333 下都**不显著偏离随机**
（单侧精确二项：P(X≥5)=0.045，P(X≥4)=0.173）——这个「哨兵通过」只是没触发红线，
不代表 C 学到了决策。Wilson 95% 区间 C=[0.359, 0.918]、A=[0.646, 1.0]，**大幅重叠**。

## 3. 致命问题：判据 ① 实际上不可测

### 3.1 只有 1/7 个决策点有样本，且「真实标签」并非真实决策日志

本机复核 `data/sft/*.jsonl`：

```
json_tasks.jsonl  n=300  validation 全 PASS  rows_with_decisions=0
code_tasks.jsonl  n=63   validation 全 PASS  rows_with_decisions=0
→ 全库 steps[].decisions 为空
```

v2 的 `--decision-policy real` 是从 `decision` 类 50 条样本的**答案 JSON** 里反推 `{"decision":"FR"|"RW"|"PATCH"}`，
再写成 `<D:EDIT=...>`。所以：

- 只有 `EDIT` 一个决策点有标签，其余 6 个点（`CTX/FIX/NEXT/PLAN/RETRY/SAFE`）`no_samples`；
- `validation` 全 PASS，8 类 `<V:ERR=...>` 一个正样本都没有；
- 训练序列决策密度 **0.000932（0.093%）**，比方案 §8.5 要求的 1%—2% 区间**低一个数量级**。

这意味着「阶段一词表共存」的核心前提根本没被构造出来：19 个决策 token 里只有 3 个（`<D:EDIT=*>`）被训练过。
`docs/方案一 §7` 的判据 ① 要求「探针在**每个决策点**上分别报 top-1 再宏平均」，
当前 `macro_accuracy=0.7143` 只是 `EDIT` 单点的 5/7，**不是宏平均**。用它和 A 组比，等于拿 1 个点的成绩去判整个空间。

### 3.2 探针特征退化成一个常数

本机逐位置统计 `build_ids()` 的输出：

```
train 决策 token 前一 token 分布: {'</TASK>': 35}
test  决策 token 前一 token 分布: {'</TASK>': 7}
决策 token 前最近控制 token / 距离: {('</TASK>', 1): 50}   ← 50/50 全是紧邻
```

因为 `build_ids()` 把决策 token 紧跟在 `</TASK>` 之后、`<CODE>` 之前，
**pos-1 永远是 `</TASK>` 这一行 hidden**。探针看到的 35 条训练特征，是「同一段任务文本 + 固定结构位置」的表示，
不是「决策即将发生时的上下文状态」。判据 ① 想验证的是「决策信息是否进入共享表征」，
但这里测的是「任务文本能否被线性映射到 FR/RW/PATCH」——A 组（外挂分类器）做的恰恰就是这件事，
而且它用 390419 参数专门拟合，C 组探针只有 579 参数。**C 输给 A 是结构性的，不是表征输了。**

### 3.3 A 组的 1.000 是记忆，不是泛化

本机核对 `decision` 类 50 条样本的 task 文本：

```
唯一 task 数: 19       归一化后唯一模板数: 19
decision train 唯一: 19   test 唯一: 6   完全重合: 6
test 样本与 train 最相似 task 相似度 >0.8 的比例: 6/6 (全部 1.00)
```

**test 里的 6 个 task 文本在 train 里一字不差地出现过**，只是配了不同的具体变量名/行号。
`stratified_split()` 按 `category` 随机打散，没有按「模板簇」分组，导致同一模板的变体跨 train/test 分布。
所以：

- A 组 7/7=1.000 很可能是「背下了 19 个模板 → 关键字 → 答案」的映射；
- C 组 5/7=0.714 同样被这个泄漏抬高；
- 两者之差（差 2 条）在这个样本量下没有统计意义（区间重叠，见 §2）。

**一个诚实的外挂基线，test 必须是 19 个模板里完全没见过的模板。**

### 3.4 判据 ① 的判定逻辑还有一处自相矛盾

`judge()` 里有天花板保护：

```python
elif c["macro_accuracy"] >= 0.99 and a >= 0.99:
    → unknown（天花板效应，不构成证据）
```

但当前 A=1.0、C=0.714 不触发它，于是走进 `c >= a` 的硬比较并直接判 `fail`。
也就是说：**如果 C 也考到 1.000（比如把探针换成记忆任务文本），判据会正确记 unknown；
而 C 考 0.714 反而被判成「方案失败」。** 分数更低反而得到更强的否定结论，逻辑上站不住。
正确做法是：当「唯一有样本的点」+「n_test < 30」+「train/test 模板重合」任一成立时，
判据 ① 直接记 `unknown` 并说明不可测，而不是给 fail。

## 4. 判据 ③ 的 0.875 有幸存者偏差，且低估了失败率

### 4.1 分母只数「没被截断」的生成

`eval_generation()`:

```python
counted = [r for r in free if not r["truncated"]]        # 排除 truncated
structure_rate = sum(ok for r in counted) / len(counted)
```

`metrics.json` 里的 `n_counted` 没打进 stdout，但可由 `0.875` 反推：
分母需满足「≥30 门槛」且 ≤52，且 `0.875 = n_ok/n_counted` 为整数解，
故 `n_counted ∈ {32, 40, 48}`，对应 `n_truncated ∈ {20, 12, 4}`，`n_ok ∈ {28, 35, 42}`。
三种可能都说明**至少 4 条、至多 20 条生成被截断**，且都低于 95% 阈值。

但 `generate()` 的停止条件是「吐出 `<V:...>`（C 组）或 `</CODE>`（B 组），或撞上 `max_new_tokens=160`」。
**撞上限被截断的生成，必然没吐出 `</CODE>` / `<V:PASS>`，`check_structure()` 必判非法**
（本机验证：未闭合 CODE → `CODE 标记数不对 open=1 close=0` + `CODE 段未闭合` + `结尾不是 <V:...>`）。
把这些按失败计入分母（全 52 条）：

```
n_counted=32 → 28/52 = 0.5385
n_counted=40 → 35/52 = 0.6731
n_counted=48 → 42/52 = 0.8077     ← 三种可能全都 < 0.95
```

也就是说，**无论 `n_counted` 具体是多少，按「模型输出」口径的真实结构合法率都过不了 95%**，
而脚本报的 0.875 已经是「挑过分母」之后偏高的那个数。（把 `metrics.json` 里的
`n_counted`/`n_truncated` 一起贴出来即可定死是哪一种。）

脚本自己在 caveat 里写了「仅统计未截断生成」，但**判据 ③ 的阈值 95% 是针对「模型输出」的**
（`docs/探针实验设计.md` §4：`parse_sequence()` 不抛错且 `validate()` 为空的比例；`use 本仓库 CLI 批量跑`），
不是针对「模型恰好在 160 token 内收敛的那些输出」。截断就是一次失败输出，不该从分母里拿掉。

> 另有一处口径漂移：§4 要求用 `src/lightprism/sequence.py::parse_sequence + validate()`，
> 脚本用的是内联 `check_structure()`（自造的一套规则，例如「验证 token 没紧跟 `</CODE>`」）。
> 两者不等价，报告里应显式声明差异，否则「结构合法率」不可比。

### 4.2 0.875 本身也不是模型学不会，是生成预算不够

`max_new_tokens=160`，而训练集 `mean_len=147.9 / max_len=662`，
答案 JSON 又长（`reason` 字段 + 格式化）。20/52 撞上限是**预算问题**，不是语法能力问题。
把 `max_new_tokens` 提到覆盖 95 分位序列长度再测，才有意义。

## 5. 判据 ② 的「pass」差 1 条，且不测它声称测的东西

本机复核 eval 的 52 条 test：`json=42 / code=10`，所以代理样本 n=42（满足 ≥30 门槛）。

```
C = 0.191 → 8/42
B = 0.167 → 7/42
差距 = 1 条样本
```

- 判据 ② 的原文是「生成代码**一次通过率** ≥ B 组」，口径 `map_diagnostics([]) == PASS`（`light ai check --json --run`）。
  OpenI 没有光明解释器，脚本用「CODE 段 `json.loads` 成功且与标准答案相等」作代理——
  这是 **JSON 精确匹配**，不是「代码通过检查器」。判据名已经在输出里写成「JSON 精确匹配代理」，
  但仍挂在「一次通过率」编号下，容易误读。
- 8/42 vs 7/42 差 1 条：McNemar / 二项检验下完全不显著，判 `pass` 没有判别力。
- 脚本里其实有「0 >= 0 记 unknown」的保护，但没覆盖「差 1 条」这种擦边。
  ≥30 样本门槛只保证了「分母够大」，没保证「差距够大」。
- caveat 已经诚实写了「真实一次通过率 unknown、光明代码类 63 条不并入」，
  但结论表里那条 `pass` 仍会被当成绿灯。**建议：判据 ② 本轮直接记 unknown。**

## 6. 判据 ④ 是唯一可信的绿灯，但也只对了一半

- 密度 0.0020（生成序列口径）/ 0.000932（训练序列口径）都 ≤ 0.02，**但方案 §8.5 要求的是 1%—2% 的「目标区间」**，
  不是「越低越好」。0.09% 说明数据里几乎没有决策 token，恰恰是 §3.1 的同一个病根。
- 速度下降 0.010：`speed_drop_vs_B` 用 C/B 两组 `tokens_per_s` 均值算，而 C 组序列天生多 1 个 `<V:PASS>`、
  且两组 `tokens_per_s` 都包含 Python 逐 token 生成循环开销，不是纯 kernel 吞吐。caveat 已说明「不是等 token 预算的严格对照」。
- `docs/探针实验设计.md` §4 第 40 行明确写了密度口径分歧（按段 vs 按子词）。
  报告里两个口径都列了，这点做得对。

## 7. `next_step` 指错了方向

输出给的是：

```
"next_step": "按 docs/探针实验设计.md §6 固定顺序调参后重跑"
```

§6 的四步是：词表预算 → 数据配比 → 嵌入初始化 → 探针训练数据分布。
这四步**全都假设「已有真实决策标签、7 个点都有样本」**。当前是：

| §6 步骤 | 现在能不能做 |
|---|---|
| ① 词表预算（密度 vs 准确率相关性） | 不能。密度恒 0.09%，准确率只有 1 个点，画不出相关性 |
| ② 决策/代码共现比例 | 不能。共现只发生在 `EDIT` 且位置固定（紧跟 `</TASK>`） |
| ③ 嵌入初始化 | 能做，但没意义：19 个决策 token 里 16 个从没被训练过 |
| ④ 探针训练数据分布 | 部分相关，但根因是 train/test 模板泄漏，不是「分布不匹配」 |

**真正该先做的是补数据，不是调参。** 而且按 `docs/样本导出.md` §4，真实决策日志目前还不存在：

> 「修复样本只能从记录了**编辑前后**的日志里来……现状：`lightharness` 目前没有这种日志格式……
> 在拿到那个格式之前，写一个『猜格式』的解析器没有意义 —— 会产出一批看起来像样本、实际字段全错的数据。」

`docs/样本导出.md` §2.2 已经证明 `light ai check` 归档**只产出失败样本、导不出修复样本**
（`source_hash` 对出错那一刻的源码算，代码改好了 hash 就变，永远匹配不上）。
所以「真实 `<V:PASS>` 后的修复配对」这条路是断的，必须先定义日志格式。

## 8. v3 修复方案（按优先级，先数据后调参）

### P0 · 门禁：在补齐之前不许报 fail / 不许进阶段二

`judge()` 增加前置门禁，命中任一即把**整个 verdict 记 `incomplete`（而非 fail）**，并在 checks 里逐条标 `unknown`：

```python
blocking = []
if len(c["points_with_test"]) < 7:  blocking.append("决策点覆盖 < 7")
if c["n_test_rows"] < 30:          blocking.append("探针 test 样本 < 30")
if train_test_template_overlap:     blocking.append("train/test 决策模板重合")
if validation_codes_seen == ["PASS"]: blocking.append("8 类 <V:ERR> 无正样本")
```

理由：当前 `verdict=fail` 会被读成「方案被否定」，但证据等级只有 `partial_coverage`，
四条判据没有一条具备判别力。**`fail` 这个词的强度现在超过了证据强度。**

### P0 · 数据：按模板簇分组切分，堵住泄漏

`stratified_split()` 增加 `group_key`：对 `decision` 类用归一化后的 task 模板（19 个簇）做 `GroupShuffleSplit`，
保证 test 里出现的是**训练中完全没见过的模板**。同理适用于 6 类 JSON 任务（都是固定模板展开）。

验收：本机脚本打印 `decision train/test 模板重合 = 0`，A 组在这种切分下重测才有资格当基线。

### P0 · 数据：补 7 个决策点与 8 类验证 token 的正样本

两条路，选其一或并行，**且必须标明证据等级**：

1. **真实日志（首选，但要先建格式）**：按 `docs/样本导出.md` §4 给 `lightharness` 定义「编辑前后」日志
   （文件路径 / `EDIT=FR|RW|PATCH` / 前后 check 结果 / 任务 id / 时间戳），再写导出器。
   这条路能同时给出 `<V:ERR=...> → <V:PASS>` 配对，是唯一能支撑判据 ② 真实口径的来源。
2. **合成机制验证（过渡，不许报 pass）**：`--decision-policy rule` 已经实现 7 点轮转注入（每条 2 个点、密度 ~1.3%），
   且 `judge()` 已把 `evidence_level` 锁成 `mechanism_only`。**v3 应把 rule 作为默认跑一次机制回归**，
   用来验证「命名空间隔离 / 探针可读性 / 密度上限」，但报告里明写「不证明真实决策能力」。
   注意 rule 的标签是**从答案 JSON 和任务文本关键字确定性推出**的，
   探针/A 组仍能靠任务文本抄到，所以同样要做模板分组切分。

### P1 · 口径：修判据 ③ 的幸存者偏差

```python
# 截断 = 一次失败输出，计入分母
all_free = free
structure_rate = sum(1 for r in all_free if r["structure_ok"] and not r["truncated"]) / len(all_free)
```

同时：
- 把 `max_new_tokens` 提到覆盖训练序列 95 分位长度（当前 160 → 建议 ≥ 320，并单独报 `n_truncated`）；
- 用 `src/lightprism/sequence.py::parse_sequence + validate()` 复核一遍，
  与内联 `check_structure()` 并列报数，差异写进报告；
- ≥30 门槛保留，但增加「差距显著性」检查：C/B 精确匹配差 < 3 条时记 unknown（覆盖 §5 的 1 条擦边）。

### P1 · 口径：把判据 ① 变成可测

- 探针特征改为**多位置对照**：`pos-1`（`</TASK>` 表示）、
  `pos-2`（任务文本末）、`last_task_token`（任务语义）分别报，
  并显式记录「当前 50/50 决策 token 紧邻 `</TASK>`」这一事实；
- 在 `build_ids()` 里把决策 token 位置做**随机插入**（方案 §7「随机交错三类 token」），
  而不是永远紧跟 `</TASK>`——否则 pos-1 是常数，探针永远测不到「决策前的上下文状态」；
- A 组基线换成两种：`(a)` 纯任务文本分类器（当前实现）、`(b)` 冻结主干 + 同位置 hidden 的 MLP，
  两者都报；只跟 `(a)` 比是拿 579 参数去比 390419 参数。
- 天花板保护从「C 和 A 都 ≥0.99」放宽为「任一组 ≥0.95 且 n_test<30 → unknown」。

### P1 · 判据 ②：本轮改记 unknown，并把真口径接回来

- 报告里把「JSON 精确匹配代理」与「真实一次通过率」分成两列，不再共用一个编号；
- 光明代码类 63 条现在记 unknown（`_format=code`），等 `light ai check --json --run` 可在目标环境跑时补上；
- 或者把「一次通过率」代理改为「生成 CODE 段能被 `light ai check` 静态检查通过」的本地可测子集，并注明与 `--run` 的差异。

### P2 · 补方案 §7/§8 要求但脚本缺的检查点
