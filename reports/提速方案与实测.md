# 推理提速方案与实测（T-0340，V4 ≥200 tok/s）

> 交付日期：2026-11-12 · 代码仓：`lightprism` · 被测配置：`configs/demo-3m.json`
> （d=192 / L=6 / H=6 / hd=32 / V=4096 / FFN 512，3,443,520 参数）。
> 本文所有 tok/s、ms/token 均由 `scripts/bench.py` 实测产出；估算值单独标注，不与实测混用。

## 一、结论（先看这一段）

| 判据 | 要求 | 本机实测（FreeBSD .88，单线程口径） | 结论 |
|---|---|---:|---|
| V4 吞吐（demo-3m，200 token） | ≥200 tok/s | **72.8 – 102.3 tok/s，中位 101.5**（5 次） | ❌ **未达标** |
| `--min-tok-s` 阈值断言 | 默认 0 行为不变；低于阈值 exit 1 | 单测 5 项通过；退出码实测 1 / 0 / 0 正确 | ✅ |
| 既有回归 | 不破坏 KV cache / 模型正确性 | `test_model.py` 28 项 + `test_kv_cache.py` 4 项通过 | ✅ |

**本卡结论：demo-3m 在本机（Ivy Bridge EP，无 AVX2，OpenBLAS 版 torch）上物理上达不到
200 tok/s。** 不是测量口径问题，也不是只改 bench 能变绿的问题；纯矩阵乘地板已实测为
3.21 ms/步（理论天花板约 311 tok/s），而端到端实测约 9.8 ms/步，中间 6.3 ms 是归一化 /
RoPE / 激活 / 视图拷贝 / Python 调度等非矩阵乘开销，纯 torch 路径无法把它压到达标所需的
1.79 ms 以内。目标机（Broadwell，有 AVX2）实测留待 T-0342，本卡不放宽判据。

## 二、复盘：计划书 §1.1 的 283 tok/s 为什么和实测 77.8 差 3.6 倍

### 2.1 两个数字的口径根本不同

| 维度 | §1.1 合成基准（283 tok/s，3.53 ms/token） | 端到端真实 decode（本仓实测） |
|---|---|---|
| 测量对象 | 逐 token 的**矩阵乘规模估算**（按 FLOP / 带宽推算） | 真实 `incremental_forward` 整步前向 |
| 张量形状 | 单层线性层 GEMM 形状，单独计时 | T=1 的极小 decode 张量，逐层串联 6 层 |
| 线程口径 | 表注标注 12 线程 | **单线程**（验收口径，写死在 bench.py） |
| 包含算子 | 仅 GEMM | 嵌入、QKV/投影/FFN 全部 GEMM **外加** 4 类 RMSNorm、Q/K-Norm、RoPE、SDPA、SwiGLU 激活、残差、视图/连续化拷贝、argmax |
| BLAS 假设 | 隐含向量化 BLAS（MKL/oneDNN 级） | 本机 torch：**BLAS=open（OpenBLAS 0.3.33），CPU capability=DEFAULT，无 MKL/oneDNN 向量化路径** |
| 调度开销 | 不计 | 每个 `nn.Module.__call__`、张量分配 / 释放、视图切片的固定开销在小张量上被放大 |

### 2.2 3.6 倍差距的拆解（本机实测，见 §四）

- **纯 GEMM 地板**：把 6 层所有 Linear 拆出来单独计时求和 = **3.213 ms/步**
  （理论天花板约 311 tok/s）。这是本机这套 BLAS 下矩阵乘本身的下限。
- **端到端实测**：约 **9.6–9.8 ms/步**（中位 101.5 tok/s）。
- **非 GEMM 开销**：约 **6.3 ms/步**，来自归一化、RoPE、FFN 激活、KV 拼缓存、
  注意力输出连续化拷贝、Python/模块调度与分配器 churn。
- 也就是说：合成表只算了 GEMM 那 3.2 ms 的部分，**漏掉了真实 decode 里约 2/3 的开销**；
  再叠加本机无 AVX2、OpenBLAS 单线程小矩阵效率偏低，最终实测只有估算的约 1/3。

> 结论：§1.1 的 283 tok/s 是「规模上界估算」，不能当作本实现端到端可达的吞吐承诺；
> T-0331 卡面曾以「bench 没有阈值断言」把 74–97 tok/s 判 done，正是缺少这道口径闸门
> （本卡已补 `--min-tok-s`，见 §五）。

## 五、本卡落地 / 否决的提速路径

### 5.1 已落地：RoPE 余弦/正弦表惰性预计算（`src/lightprism/model.py`）

- **改动**：RoPE 表按 `max_seq` 一次性惰性构建并缓存为模型张量，decode 每步只按位置
  切片；原先每步都重建 `inv_freq` / `arange` / `outer` / `cos` / `sin` 一整套小张量。
- **实测收益**：在测量噪声区间内（优化前 87.1/103.1/78.3，优化后 102.0/96.9/102.3/
  72.8/101.5），**没有可辨识的稳定提速**；该路径只去掉逐步表重建的分配开销，不碰 GEMM
  与主链路。正确性由 `test_kv_cache.py` 4 项（增量与全量 logits 在 1e-4 内一致）兜住。

### 5.2 已落地：bench 阈值断言 `--min-tok-s`（`scripts/bench.py`）

- 新增 `--min-tok-s N`，**默认 0（不校验，行为与旧版完全一致）**；实测 tok/s 低于阈值时
  退出码 1，达到 / 超过退出 0；`--json` 输出里带 `threshold.min_tok_s / passed` 字段。
- 测试：`tests/test_bench_threshold.py` 5 项（默认阈值不失败、低于阈值 exit 1、达标 exit 0、
  边界恰好等于达标、CLI 默认值为 0）。测试用 monkeypatch 固定合成吞吐，不绑本机硬件性能。
- 实测退出码：`--min-tok-s 200`（实测 ~100）→ **exit 1**；`--min-tok-s 0` → **exit 0**；
  `--min-tok-s 10`（实测 ~100）→ **exit 0**。

### 5.3 评估后否决 / 不可行的路径

| 路径 | 评估结论 | 证据 |
|---|---|---|
| 换 MKL / oneDNN 版 torch 构建 | **本机不可行**：FreeBSD 无预编译 MKL/oneDNN torch wheel；且 Ivy Bridge 无 AVX2，即便换 BLAS 也受限于无 AVX2 天花板。属环境级改造，不在本卡允许路径内 | torch `__config__`：BLAS_INFO=open，CPU capability=DEFAULT |
| INT8 / 动态量化 | **该构建无量化引擎**：`quantize_dynamic` 报 `Didn't find engine for operation quantized::linear_prepack NoQEngine`（无 fbgemm/qnnpack 后端） | 探针 `probe5.py` 复现 |
| 多线程 | **无增益反变慢**：12 线程 77.1 tok/s < 单线程 101.5 | §4.3 |
| 砍模型规模（d=128 / L=4，合成表估 564 tok/s） | 计划书 §1.1 同口径已被本实现端到端实测推翻；且改动规模必须同步 configs 并评估对 V2 训练合法率的影响。**本卡不改 `demo-3m.json`**，留作后续专项 | §2.2、T-0334 §5.6 |
| 算子融合自定义内核 | 需要 C++/自定义扩展内核，超出「只依赖 torch、不引重依赖」的本仓约束，本卡未做 | — |

## 六、为什么本机到不了 200 tok/s（瓶颈定性）

1. **GEMM 地板已接近目标线的 1.6 倍**：纯矩阵乘就要 3.21 ms/步；200 tok/s 要求整步
   ≤5.0 ms，留给所有非 GEMM 算子的预算只有 1.79 ms，而实测非 GEMM 约 6.3 ms。
2. **非 GEMM 开销是小张量上的固定调度 / 元素级内核开销**：RMSNorm、RoPE、SwiGLU 激活、
   视图拷贝在 T=1、hd=32 的极小形状下，算子数量与每次调用的固定成本占比高于矩阵乘本身；
   纯 torch 没有算子融合能力，无法把这些小内核合并。
3. **BLAS 向量化受限**：本机无 AVX2，torch 走 OpenBLAS 的 DEFAULT 路径，小矩阵单线程效率
   偏低（同形状裸 `mm` 历史记录：torch 0.088 ms vs numpy 0.038 ms，慢约 2.3 倍）。
4. **多线程无法绕开**：decode 阶段同步开销主导，加线程反而更慢（§4.3）。

## 七、后续建议（不在本卡改动范围）

- **T-0342 目标机实测**：在 Broadwell（有 AVX2）真机上跑同一 `bench.py --min-tok-s 200`，
  那才是 V4 对外承诺的口径；本机数字不能外推到目标机。
- 若仍需在老 CPU 上追吞吐：优先评估**更小模型规模**（d=128 / L=4 一档）对 V2 合法率的
  影响，再决定是否出新 config；其次评估带 MKL/oneDNN 的 Linux + AVX2 运行环境。
- 推理核后续可考虑：KV 缓存预分配（消除每步 `cat` 历史拷贝）、w1/w3 单 GEMM 打包，
  两者预计均为个位数百分比收益，不改变本机不达标的定性结论。
