## 五、未观测项与原因（如实列出，没有拿标注硬凑）

| 未观测项（test 侧） | 为什么没出现 | 能不能补 |
|---|---|---|
| `SAFE=L1` / `SAFE=L2` | `engine.py` 里 SAFE 恒发 `L0`：本卡所有动作都是本地临时文件 + 只读模板，没有需要人工确认或高危写盘的动作。要出现 L1/L2 得先引入真实写盘/外部调用类动作 | 需新能力，不是加数据能解决的 |
| `FIX=ADD_TYPE` / `FIX=RENAME` | FIX 方向由诊断码决定：`L2001/L2002/L2003/L4001 → ADD_TYPE`、`L4002 → RENAME`，而这些码映射到的验证码是 `ERR=MISSING_TYPE`，**不在可观测验证码集合**（`PASS/ERR=RUNTIME/ERR=CHECKER_FAIL`）。引擎按现有口径把这类失败记为 `ERR=CHECKER_FAIL`，于是 FIX 只能走 REFACTOR | 要么放宽验证码口径（本卡明令禁止改验收口径），要么等 `ERR=MISSING_TYPE` 进入可观测集合 |
| `NEXT=ASK` | 只在「重试额度耗尽仍失败」时出现。test 侧没有放这类任务（必失败任务集中在 train 侧），所以全量 212 条里 ASK 5 条全在 train（E02、E11—E14 的第 3 次 attempt） | 可在 test 侧加 1 条必失败任务，代价是 test 侧多 3 条 ERR 记录 |
| `CTX=DROP` | 需要「top1 候选缺槽被丢弃」的诱饵任务。9 条诱饵（T51—T59）登记在 train 侧 family | 把其中 3 条移到 test family 即可，重复率会小幅上升 |
| `CTX=FETCH` | 需要同一任务第 2 次检索换候选，只在 E02/E11—E14 的第 2/3 次 attempt 出现（test 侧这 5 条登记在 train family） | 同上 |
| `EDIT=FR`（整体仅 1 条，且是历史记录） | 新版 light 给的 `L3001` 诊断都带行号，引擎优先走行级补丁 `PATCH`；只有诊断不带行号才走 `FR`。FR 分支有单测覆盖（`test_runtime_oob_triggers_real_find_replace_retry` 断言 `edit_mode == "FR"` + `find_replace`），但真实数据里没有「无行号诊断」的任务 | 需要构造一个只给 `L3001` 不给行号的 checker 场景 |

> 一句话：这 7 项里 `SAFE=L1/L2`、`FIX=ADD_TYPE/RENAME` 是**能力/口径**边界（本卡不允许动），其余 5 项是**数据摆放**的取舍，下一卡可以补。

### 6.1 定因：链路已接线，问题在码表 pattern 与报错文本

卡面要求分清「规则未接线 / priority 被兜底吃掉 / check 只跑某一 stage」三种可能。实测结论是**都不对**，真正的原因是第四种：**正则 pattern 与 light 实际产出的报错文本对不上**。

- **接线证据**：`cli/light.py:1950`（边框块）与 `cli/light.py:1996`（单行）都会走 `_ai_explain(message)` → `src/diagnostics/registry.py:412 explain(message)`；`explain()` 用每条 `Rule.pattern` 匹配**原始报错文本**，匹配不上才由 `cli/light.py:1961/2012` 发 `L0000`。码表里没有任何兜底优先级规则，所以**不存在「priority 被兜底吃掉」**。
- **stage 也不是问题**：语法检查 stage 实测跑到了（3 条 `stage=语法检查`），并且 `L2002` 正是在语法检查 stage 命中的，说明该 stage 的码表在工作。
- **真正的缺口**（2026-11-16 补跑 5 条定向片段）：

| 目标码 | 定向片段 | 实测码 | light 真实报错文本 | 为什么没命中 |
|---|---|---|---|---|
| `L1001` | `def 加一(甲)：\n  返回 甲 加 1。` | `L0000` | 无法识别的语法元素：`'：'` | pattern 只认 `def`/`function` 关键字名 |
| `L2001` | `段落 加一 接收 甲：\n  返回 甲。\n打印(加一(1, 2))。` | `L0000` | ⚠ 警告：参数 `甲` 缺少类型标注 | pattern 认「参数数量错误」，实际报缺类型警告 |
| `L2003` | `段落 加一 接收 甲 为 1：\n  返回 甲。\n打印(加一())。` | `L0000` | 期望 冒号「:」，但得到 数字 | pattern 认默认参数写法，实际是 parser 冒号报错 |
| `L4001` | `设 甲 为 1。\n打印(乙)。` | `L0000` | 名称错误 `name '乙' is not defined` | pattern 认中文「缺导入/该函数来自『…』模块」 |
| `L4002` | `导入《不存在的模块》。` | `L0000` | 模块未找到 `No module named '不存在的模块'` | pattern 认「从 math 导入 / print( / 没有 math 模块」 |

**定因结论**：`light` 仓 `src/diagnostics/registry.py` 的 `Rule.pattern` 覆盖面不足（只覆盖少数中文措辞，parser/运行时的英文文案与「缺类型警告」没覆盖）。修它在 `light` 仓，**不在本卡 paths** → 本卡在 `lightprism` 侧做两件事：只给实测可达的码造样本；把 20 个已登记码的结论固化成 `DIAGNOSTIC_REACHABILITY` + 回归用例 `tests/test_err_samples.py::test_probe_matrix_against_real_light`（light 哪天把规则接对了，用例会变红提醒更新矩阵，而不是让矩阵悄悄过期）。

### 6.2 回归用例怎么保证「不是伪造」

- `test_reachability_matrix_covers_every_registered_code`：`tokens.py` 里 20 个已登记码**每个都要有定因结论**（有片段并记实测码，或明确写「本轮未构造出片段」的理由），少一个就红。
- `test_reachable_codes_record_specific_code_not_l0000`：可达的码必须记**具体码**（`L3001`/`L2002`），其余 5 个明确记 `L0000`——把「L0000 冒充具体码」堵死。
- `test_probe_matrix_against_real_light`：8 条片段真跑一遍，实测码必须与矩阵一致（本机实测耗时 115s；没有 light 仓的环境自动 skip，CI 不会因缺后端变红）。
