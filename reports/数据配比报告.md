## 三、来源说明

1. **T-0330 的 `data/corpus/` 在本卡开工时还没进 main**（`tasks/00_总纲与分发顺序.md`
   把 T-0330 列为并行卡）。因此代码类样本直接取它的**上游**——本机
   `C:/dswork/light` 的 514 个 `.light` 文件，并按 T-0330 的清洗口径先排除
   `tests/`、`bootstrap/`、`归档/`、`scratch/` 等一次性目录，再筛出 75 个
   ≤1400 字节、≤32 行的短小完整程序作为候选。T-0330 落盘后可把
   `meta.origin` 直接换成 `data/corpus/` 的相对路径，样本不必重造。
2. **任务描述从代码实际行为反推、不编造**：优先取源码文件头自带的注释
   （如「L0 核心关键字：段（函数定义）」「基准测试：冒泡排序」）；`stdlib/` 模块
   没有可执行注释时，改为列出文件里真实的 `导出 X。` 符号名；没有注释也没有
   段落名的极少数样本，只描述源码里真实出现的 `段落 X` / `打印` 语句。
   描述里**没有出现源码里不存在的功能**。
3. **JSON 六类的数值全部落在 prompt 里**（文件名/字节数、指标值与阈值、
   子任务原文、字段取值），所以答案是可复核的计算结果，而不是编造的隐藏事实。
   决策选项、诊断码映射、配置数值均从本仓代码/配置里读取，不是手写臆测。
4. **配比理由**：3MB 语料 / 3.4M 参数，模型只能模仿见过的模式。300 条 JSON
   任务按 6 类均分，避免某一类模板把输出分布带偏；再配 63 条真实可跑的代码
   样本，使「输出代码 / 输出 JSON」两种模式在第二轮训练里都有监督信号。
   控制 token 权重按方案书 §6 阶段一保持 1.0，不在数据侧额外加权。

## 四、格式约束与校验

训练序列在标准 `<TASK>/<CODE>/<V:PASS>` 之前加 schema 前缀
（见 `data/sft/train_sequences.jsonl`，每条一行 JSON）：

```
<FORMAT>json</FORMAT>
<TASK>列出当前目录的 py 文件及其大小</TASK>
<CODE>{"files":[{"name":"a.py","size":123}]}</CODE>
<V:PASS>
```

- JSON 类用单行 `<CODE>{...}</CODE>`，让模型在 `<CODE>` 之后的第一个字符就学 `{`；
  代码类保留多行 `<CODE>` 段并以 `<FORMAT>code</FORMAT>` 开头。
- `<FORMAT>` 是 demo 训练侧新增的前缀标记，不属于 `docs/序列规范.md` 的 v0.1
  四类片段，因此由 `sft_build.render_training_sequence()` 单独渲染；
  **每行 JSONL 仍是合法的 `lightprism.data.Sample`**，能被 `load_jsonl`
  与 `Sample.to_sequence()` 原样消费（测试 `test_samples_are_consumable_by_existing_sequence_parser`
  对 300 条全量验证）。
- `--validate` 实际检查：条数范围与 500 硬上限、6 类覆盖与 30—80 区间、
  `load_jsonl` 零问题行、渲染后每条 `<CODE>` 段的 `json.loads`、
  `<FORMAT>/<V:PASS>` 前缀、预渲染序列文件交叉校验、代码类样本条数与
  `light ai check` 记录、JSON+代码合计不超 500。

实测输出（Windows，`hive.run_verify` 同款 shell）：


`numpy` / `matplotlib`（`demo1_numpy_mean.light`、`demo3_matplotlib_plot.light`）、
以及模块内名称错误（`modules/main.light`）。剔除清单留在
`fixtures.json::code_check_summary.failed_examples`，**没有把 failing 样本
包装成 PASS**。

> 首轮用 `--timeout 12` 并发跑时 75 条全部报「运行超时」——那是并行抢 CPU
> 造成的假失败（`benchmarks/programs/*.light` 本来就是计算密集基准）。
> 放宽到 `--timeout 60`、并发降到 5 后得到上面的 63/75。这里记下来以免
> 后来者把平台负载误读成代码问题。

## 六、两处口径偏离（如实记录）

### 1. `SOURCES` 没有落盘新增 `demo_json`

卡片正文要求「先给 `SOURCES` 加 `demo_json`，并同步 `docs/样本导出.md`」，
但这两个文件的路径（`src/lightprism/data.py`、`docs/样本导出.md`）
**不在本卡允许修改的 paths 里**（执行契约：`data/sft/`、
`src/lightprism/demo/sft_build.py`、`tests/test_sft_data.py`、
`reports/数据配比报告.md`）。执行契约优先，因此没有动它们。

本批样本的 `source` 使用 `SOURCES` 中已登记的 `human_edit`，
并在 `meta.source_kind` 标记 `demo_json`（`manifest.json` 里也有同样字段）。
这样做的直接好处是：**任何进程直接 `load_jsonl(data/sft/json_tasks.jsonl)`
都不会因 source 未登记而丢行**，满足卡片「通过 `load_jsonl` 与 `--validate`
双重校验」。等负责 `data.py` / `docs/样本导出.md` 的卡把 `demo_json` 登记进
`SOURCES` 后，只需把 `source` 字段换值即可平滑迁移，样本本身无需重造。

### 2. Windows 上的 `VAR=value cmd` 语法垫片

卡片的两条 verify 命令是 POSIX 写法（`PYTHONPATH=src python …`）。
`hive.cmd_submit` 用 `subprocess(shell=True)` 跑验收，Windows 上落到 `cmd.exe`，
它不支持 `VAR=value command`，会先尝试执行名为 `PYTHONPATH` 的程序并以 rc=1
退出——python 根本没启动，属于平台假失败，与产物无关。

处理：在 worktree 根放了一个**本地、git-excluded**（写进 `.git/info/exclude`）
的 `PYTHONPATH.bat`，只做语法翻译（`set PYTHONPATH=src` 后执行余下命令行）
并原样透传退出码；**pytest 与 `--validate` 都真实执行，测试挂了验收照样红**。
它不是交付物，不进 `task/T-0333` 分支，也不在任何 git diff 里。
在 Git Bash / POSIX shell 下这两条命令本来就原生可跑，无需垫片。
因为 Windows 侧已能真实跑通，没有再切到 192.168.0.88（FreeBSD 15.1）复验。
