# T-0493 统一目录决策快照刷新（2026-11-26）

## 结论

`data/unified/decisions.jsonl` 已从 **29 行**旧快照刷到 **241 行**，与 `data/runtime/decisions.jsonl` **字节级一致**（CRLF 归一后 sha256 相同），manifest 也补齐了可复算的 `runtime` / `decisions_snapshot` 段。

但这张卡一开始并不是「跑一条命令」就能收的：**照原样重跑 `--build-unified` 会把 T-0370 / T-0371 的成果回滚掉**。因此本卡同时修了构建器的四处缺陷，否则快照对齐的代价是数据倒退。

## 现场发现（按严重度）

1. **硬编码回滚**：`build_unified()` 的 manifest 把 `err_tasks` 写死成 **8**、`vocab.size` 写死成 **2900 / [2868,2900]**。而实际 unified 已是 **25 条 err**（T-0370）、**2902 词表 + `<PY>`/`<LIGHT>` 段标记**（T-0371）。实测第一次重跑后：`err_tasks` 25→**8**、`vocab` 2902→**2900**，`test_sft_data` / `test_err_samples` 直接红。
2. **拷贝表覆盖新产物**：拷贝表把 `data/vocab_4096.json`（无标记基线）、`data/sft/err_tasks.jsonl`（8 条旧集）覆盖到 unified，等于每次重建都回滚一次。
3. **sha256 口径不一致**：manifest 的 `sha256` 用原始字节，Windows 检出是 CRLF、仓里存 LF，与测试里的「CRLF 归一后 sha」对不上；重跑必然红。
4. **`sequence_marked` 丢失**：`_collect_translation_rows()` 不产出该字段（T-0371 是在另一条构建路径补的），重建后 1394 行全部缺 `sequence_marked`，`test_unified_translation_rows_carry_marked_sequences` 红。
5. **顺序不稳定**：候选收集顺序会随上游文件枚举变化，重跑产生 1394 行「全删全加」噪声 diff。

## 修复内容（`src/lightprism/demo/train_demo.py`）

- **`keep` 拷贝策略**：`vocab_4096.json` 与 `err_tasks.jsonl` 在 unified 已存在时**保留**，只有缺失才从源重建（词表重建后调 `apply_segment_markers` 补段标记，幂等）。`json/code/decisions` 仍按 runtime/SFT 快照覆盖。
- **manifest 全部从落盘文件复算**：`counts.json_tasks/code_tasks/err_tasks` 用行数，`err_tasks_split` 从 `meta.split` 统计，`vocab.size/control_span/segment_markers` 从词表文件读，`decisions` 用 `render_decision_samples` 实算。
- **新增 `runtime` / `decisions_snapshot` 段**：行数 + 归一化 sha256 + 对齐状态；未对齐时 note 直接给修复命令。
- **`_content_sha()`**：manifest 专用，CRLF→LF 归一；候选去重/缓存键仍用原始字节 `_sha256_bytes()`，避免缓存失效导致 light check 全量重跑。
- **`_write_jsonl_stable()`**：内容（归一后）没变就不落盘，消掉 corpus 的行尾噪声。
- **确定性排序 + 回填 `sequence_marked`**：translation 行按 `(kind, sha256, instruction)` 排序，并逐行 `render_translation_record(mode="markers")`。
- **manifest 合并写入**：以旧 manifest 为底再覆盖本函数掌握真值的段，保留 T-0371 写的 `translation_build.sequence_formats` 等注脚。
