# T-0347 训练报告 v2：CPU 重训 demo 决策层（跑够步数 + 合并对照语料与真标签）

> 状态：可交付　|　任务：T-0347　|　基线：[训练报告.md](训练报告.md)（T-0332，50 步）
> 数据：`data/unified/`（manifest 见 `data/unified/manifest.json`）

## 一、结论先说

1. **50 步的「loss 只到 6.05 / 生成全是空格」不是模型容量问题，是没跑够。** 相同模型核
   （3,443,520 参数）从 50 步拉到 **3000 步** 后：train loss **8.08 → 1.26**，
   val loss **4.82（步 100）→ 2.69（步 2100）**，生成从「空格」变成**能产出结构合法、
   `light ai check` 判 `ok=true` 的光明代码**（4 条固定 prompt 里 2 条）。
2. **3000 步内没有观察到过拟合起点。** val 在步 2100 触底 2.69325，之后到 3000 步
   一直贴着 2.69–2.72 平台，最大回升 0.83%（未达判定阈值 1%），`overfit_step = null`。
   因此**不能**说「3.4M 不够」；当前证据只支持「3.4M 容量尚未被 3000 步 / 1.47M token 用尽」。
3. **对照语料与真标签已经合并进统一目录**：392 个 `.light` 文件、363 条 SFT、1394 条
   带 `light ai check` 真值背书的 Python↔光明对照 / 工程体、29 条真实运行时决策日志。
4. **控制 token 占比 0.18% → 1.51%**（加权口径），决策 token 0.36%（加权）/ 0.014%（raw）。
   离卡面「决策密度 1% 量级」还有差距，原因和取舍写在 §4.3，没有靠编造标签去凑。

对照语料构建：上游 `tools/ai_copilot/sft_dataset.jsonl`（2254 行）+ `corpus_harness.jsonl`
（551 行）→ 按光明代码 sha256 去重（丢弃 1165 条重复）→ 1630 条候选逐条跑
`python -m cli.light ai check --json --no-corpus`（**语法级**，1.1–1.4 s/条）→
**1394 条 `ok=true`，通过率 85.52%**，失败条目整条丢弃，不做人工兜底。

### 3.2 2902 与 4096 两种词表口径

- demo / `train_demo.py`：`vocab_size=4096`，UNK=2900、pad=2901，控制区 `[2868,2900)`；
- `train_openi.py`：`vocab_size=2902`（UNK/pad 挤在 2900/2901，不再补齐 4096）；
- 两份产物在 `data/unified/vocab_4096.json` + `manifest.json` 里同时声明，**不互相覆盖**。

### 3.3 渲染格式

```
翻译 pair    <FORMAT>translate</FORMAT><TASK>…</TASK><CODE>Python</CODE><CODE>光明</CODE><V:PASS>
工程体       <FORMAT>light</FORMAT><TASK>…</TASK><CODE>光明</CODE><V:PASS>
运行时决策   <FORMAT>runtime</FORMAT><TASK>…</TASK><D:…>×k<CODE>源码</CODE><V:…>
错误修复     <FORMAT>err</FORMAT><TASK>…</TASK><D:…><CODE>…</CODE><V:ERR=…>
既有 SFT     <FORMAT>json|code</FORMAT><TASK>…</TASK><CODE>…</CODE><V:PASS>
```

决策 / 验证标签**只取日志里真实出现过的组合**（`PLAN/EDIT/SAFE/CTX/RETRY/NEXT` 的实际取值、
`PASS / ERR=CHECKER_FAIL / ERR=RUNTIME`），没有硬凑 7 决策点 / 8 验证码。

### 3.4 语料与标签统计（raw vs 进流后）

| 指标 | raw（去重后） | weighted（进流后） |
|---|---:|---:|
| 总 token | 1,324,030 | 1,472,000（打包后 2875 块 × 512） |
| 语料 token | 953,704（372 训练文件） | 同左 |
| SFT / 翻译 / 决策 / err 样本 | 363 / 1394 / 29 / 8 | 726 / 1394 / 870 / 40 |
| 控制 token（结构+决策+验证） | 10,971（**0.83%**） | 22,258（**1.51%**） |
| 其中决策 token | 183（**0.0138%**） | 5,290（**0.36%**） |
| 其中验证 token | 1,794 | 3,030 |
| UNK token | 876（0.066%） | 876（0.060%） |

口径说明：**raw** = 每条样本只进一次；**weighted** = `--sft-repeat 2`、
`--decision-repeat 30`、`--err-repeat 5` 之后的实际训练流。loss weight 方面，
结构 / 决策 / 验证 token 权重 **3.0**，文本 token 1.0（`--control-weight`）。

**与 1% 决策密度目标的差距（如实说明）**：真实决策日志只有 29 条 / 183 个决策 token。
要把 weighted 决策密度抬到 1%，需要把 29 条序列重复 ~85 次，控制 token 占比会被推到
2.5% 以上（超出卡面 1–2% 的区间），且会明显加剧对这 29 条序列的记忆。本卡选择
`decision-repeat=30`（控制占比 1.51% 落在目标区间、决策 0.36%），**没有用合成标签
去凑密度**。要继续提升，正确做法是扩充真实运行时日志，而不是加大重复。

### 5.1 过拟合起点

- 判定口径：val loss 相对历史最优回升 **>1%（相对）** 记为首个过拟合步。
- 结果：步 2100 之后最大回升出现在步 2600（2.71453，+0.79%），**未触发阈值**，
  因此 `overfit_step = null` —— **3000 步内没有观察到过拟合起点**。
- 对应的现实含义：3.4M 参数在这份 1.47M token 的数据上还没被喂饱；要继续涨点，
  优先加数据（尤其真实决策日志），而不是缩模型。

## 六、生成样例（最终 checkpoint）

checkpoint：`checkpoints/demo-3m/model.pt`（13 MB，含 `tokenizer_layout.base_vocab` 本体，
可独立加载）。固定 32 token 冒烟（`--smoke`）输出：

```
<D:PLAN=DIRECT><D:NEXT=TEST><CODE>
段落 加一(n)：
  返回 n。
</CODE><V:PASS>
```

（23 token，未截断，`vocab_size=4096`，`params=3,443,520`）

4 条固定 prompt、`max_new_tokens=64`、结构约束解码，代码块交 `light ai check` 判真值：

| # | prompt | 生成（截断展示） | ai check |
|---|---|---|---:|
| 1 | 计算 3 加 4 的结果，输出数字。 | `<D:PLAN=DIRECT><D:CTX=KEEP><D:RETRY=NO><D:EDIT=RW><D:SAFE=L0><CODE>设 甲 为 [4, 8, 2]。设 计数 为 计数 加 1。…` | ❌ L0000 意外的标记 |
| 2 | 将Python翻译成光明：`print('hello')` | `<D:NEXT=TEST><D:PLAN=DIRECT>…<CODE>runtime<FORMAT>runtime</FORMAT>设 a 为 1 乘以 20 加上 2…` | ❌ L0000 意外的标记 `/` |
| 3 | 修复光明代码中的错误（L3001）：列表索引越界 | `<D:PLAN=DIRECT><D:NEXT=TEST><D:RETRY=NO><D:SAFE=L0><D:CTX=KEEP><CODE>设 甲 为 [1, 2] 设 甲 为 甲[0]。遍历 甲 于 甲：如果 甲 大于 甲：…` | ✅ **ok=true** |
| 4 | 写一个加法程序 | `<D:PLAN=DIRECT><D:NEXT=TEST><CODE>段落 加一(n)：返回 n。</CODE><V:PASS>` | ✅ **ok=true** |

**成功样例（2/4）**：#3 / #4 代码块通过 `light ai check` 语法检查，且 #4 是完整、
可读的「定义函数 + 返回」结构，决策 token 前缀（`PLAN=DIRECT → NEXT=TEST`）语义正确。

**失败样例（2/4）**：#1 在 `如果` 处断句（未闭合块），#2 把 `<FORMAT>` 控制串写进了代码体
（翻译任务的 Python 段与光明段两个 `<CODE>` 块没有分清）。两者都被 `light ai check`
以 L0000 拒绝 —— 这说明**生成侧还不能上线**，但「格式 + 语法 + 决策前缀」已可被外部校验器判定，
不是基线那种「连空格都判不了」的状态。

> 口径说明：生成文本是**续写段**（prompt 已作为 `<TASK>` 放在输入里），所以冒烟报告里
> 「缺少 `<TASK>`」是评测口径问题，不是生成失败；上表只对 `<CODE>` 块做真实语法判定。

## 九、还没证明的 / 下一步

1. **没证明 3000 步是上限**：val 仍在 2.69 平台，继续加到 5000 步可能还有 0.05–0.1 的收益，
   但本卡 6 h 预算内不做外推。
2. **翻译方向仍弱**：#2 暴露「Python 段 / 光明段」混淆，两个 `<CODE>` 块的边界需要更显式的
   标记（例如恢复独立 `<PY>` / `<LIGHT>` 词表 token），这需要改词表，不在本卡范围。
3. **决策密度未达 1%**：受 29 条真实日志限制；扩日志比调重复更有效。
4. **没有做下游任务评测**：本卡只验证「可训练、可加载、结构可判」，不承诺端到端可用。
